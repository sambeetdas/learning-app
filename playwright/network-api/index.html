Network mocking, API testing and authentication

A browser page is only half of a web application: the other half is the network. Playwright sits between the page and the network, so a test can watch every request, answer requests with fake data, change real responses, fail them on purpose, and replay recorded traffic. The same library also has an HTTP client, APIRequestContext, for testing REST endpoints directly and for setting up data and logins quickly before a UI check.

This page uses ShopBot throughout: the product page adds items with fetch("POST /api/cart"), the chat streams answers from POST /api/chat as server-sent events, and /login sets a session cookie called sid. Every snippet below was run against ShopBot with Playwright 1.64 and pytest-playwright 0.10.

How request routing works

page.route(url_pattern, handler) (or context.route(...) for every page in the context) tells Playwright: "when the page makes a request whose URL matches, pause it and call my handler with a Route". The handler must then decide the request's fate with exactly one of the calls below. Press Play and switch between the tabs.

What can happen to a request

CallWhat happensTypical use
route.fulfill(json=..., status=..., headers=..., body=..., path=...)Answers the request with your response; the server never sees itMock an API, simulate errors, serve a fixture file
route.continue_(url=..., method=..., headers=..., post_data=...)Sends the request on to the network, optionally changedAdd headers, rewrite the body, point at another host
route.fetch() then route.fulfill(response=..., json=...)Performs the real request, lets you edit the response, then delivers itPatch one field of a real response, inject an HTML banner
route.abort(error_code="failed")Fails the request like a network error ("timedout", "internetdisconnected", "connectionrefused", ...)Offline and outage tests, blocking trackers and images
route.fallback(...)Passes the request to the next matching handler (registered earlier), or to the network if noneLayered handlers: a logger plus a specific mock
Register routes before the request happens. Call page.route(...) before page.goto(...) or before the click that triggers the fetch. A route added afterwards only affects later requests.

URL patterns and handler order

The first argument can be a glob string, a compiled regex or a predicate function that receives the URL. Globs match the whole URL; regexes are searched anywhere in it.

GlobMeansMatchesDoes not match
**/api/cart** = any characters including /http://127.0.0.1:8000/api/cart.../api/cart?x=1 (the query is part of the URL)
**/api/products?*? is a literal question mark; * = any characters except /.../api/products?limit=1.../api/products
**/*.{png,jpg,svg}{a,b} = alternatives.../img/logo.png.../logo.png?v=2
/api/cartA relative glob is resolved against the context's base_urlhttp://127.0.0.1:8000/api/cart when --base-url is setThe same path on another host
re.compile(r"/api/cart(\?|$)")Regex: search() anywhere in the URLWith or without a query string/api/cartoon

When several routes match, the most recently registered handler runs first. If it calls route.fallback(), the next one (registered earlier) gets the request. Try it:

Route matcher: which handler answers this request?

Untick a route to "unregister" it (like page.unroute(...)). The table lists routes in registration order; Playwright checks them from the bottom up.

calls = []

def log_all(route):                       # registered first: runs last
    calls.append(route.request.url)
    route.fallback()                      # let the next handler (or the network) decide

def mock_cart(route):                     # registered last: runs first
    route.fulfill(json={"count": 42})

page.route("**/*", log_all)
page.route("**/api/cart", mock_cart)

Mocking an API response for a UI test

UI tests that depend on live back ends are slow and flaky, and many states (out of stock, server errors, an empty list, a 10,000-item list) are hard to create on a real server. Mocking the browser's API calls lets you test how the UI reacts to each response, deterministically.

tests/test_cart_ui.py
from playwright.sync_api import Page, expect


def test_add_to_cart_updates_badge(page: Page):
    page.route("**/api/cart", lambda route: route.fulfill(json={"count": 42}))
    page.goto("/products/1")
    page.get_by_role("button", name="Add to cart").click()
    expect(page.get_by_role("status")).to_have_text("Added to cart")
    expect(page.get_by_test_id("cart-count")).to_have_text("42")


def test_out_of_stock_message(page: Page):
    page.route("**/api/cart", lambda route: route.fulfill(status=422, json={"detail": "Only 2 in stock"}))
    page.goto("/products/1")
    page.get_by_role("button", name="Add to cart").click()
    message = page.get_by_role("status")
    expect(message).to_have_text("Only 2 in stock")
    expect(message).to_have_class("error")
    expect(page.get_by_test_id("cart-count")).to_have_text("0")   # badge unchanged
# the page fixture uses --base-url, so page.goto("/products/1") works
pytest tests/test_cart_ui.py --base-url http://127.0.0.1:8000
Mock what the browser actually fetches. ShopBot renders the product cards on /products on the server, so routing **/api/products does not change that page: the browser never calls that endpoint there. Find the real calls first with page.on("request", print), the trace viewer's Network tab, or the browser's developer tools. Single-page apps (React, Vue, Angular) fetch most data from the browser, which is why mocking is so effective for them.

Mock data from files, and for the whole context

from pathlib import Path
import json

FIXTURES = Path(__file__).parent / "fixtures"

# serve a file as the body (content type inferred from the extension)
page.route("**/api/products", lambda route: route.fulfill(path=FIXTURES / "products.json"))

# or build the data in Python: easier to vary per test
products = json.loads((FIXTURES / "products.json").read_text())
products[0]["stock"] = 0
page.route("**/api/products", lambda route: route.fulfill(json=products))

# context.route applies to every page in the context, including popups and new tabs
context.route("**/api/cart", lambda route: route.fulfill(json={"count": 5}))
page.unroute("**/api/cart")        # remove one route; page.unroute_all() removes them all

route.fulfill(json=...) serialises the value and sets Content-Type: application/json; the default status is 200.

Modifying real requests and responses

Sometimes you want the real server, but slightly different. route.fetch() performs the request and returns an APIResponse that you can edit before fulfilling.

Patch a JSON response
from playwright.sync_api import Route


def add_hundred(route: Route):
    response = route.fetch()           # the real server answers
    data = response.json()
    data["count"] += 100
    route.fulfill(response=response, json=data)   # keep status and headers


page.route("**/api/cart", add_hundred)
page.goto("/products/1")
page.get_by_role("button", name="Add to cart").click()
expect(page.get_by_test_id("cart-count")).to_have_text("101")
Patch the HTML of a page
def everything_sold_out(route: Route):
    response = route.fetch()
    body = response.text().replace("In stock", "Out of stock")
    route.fulfill(response=response, body=body)


page.route("**/products", everything_sold_out)
page.goto("/products")
expect(page.get_by_text("Out of stock")).to_have_count(4)

To change the request instead, pass overrides to continue_():

def triple_quantity(route: Route):
    body = route.request.post_data_json            # {"product_id": 1, "qty": 1}
    route.continue_(post_data={**body, "qty": 3})  # dicts are sent as JSON


page.route("**/api/cart", triple_quantity)

# add a header to every API call (feature flags, test-run ids, auth for a staging gateway)
page.route("**/api/**", lambda route: route.continue_(
    headers={**route.request.headers, "x-test-run": "nightly"}))
For a header on every request you do not need a route: browser.new_context(extra_http_headers={"x-test-run": "nightly"}), or in pytest return it from the browser_context_args fixture.

Simulating errors and slow responses

Error paths are where real users get stuck and where tests are rarely written. With routing they take one line each.

def test_server_error_shows_something(page: Page):
    errors = []
    page.on("pageerror", lambda exc: errors.append(str(exc)))     # uncaught JS exceptions
    page.route("**/api/cart", lambda route: route.fulfill(status=500, body="Internal Server Error"))
    page.goto("/products/1")
    page.get_by_role("button", name="Add to cart").click()
    expect(page.get_by_role("status")).to_be_empty()
    # ShopBot calls r.json() on the HTML error body and crashes:
    # errors == ['Unexpected token \'I\', "Internal S"... is not valid JSON']


def test_offline_add_to_cart(page: Page):
    page.route("**/api/cart", lambda route: route.abort("internetdisconnected"))
    page.goto("/products/1")
    with page.expect_event("requestfailed") as failed:
        page.get_by_role("button", name="Add to cart").click()
    assert failed.value.failure == "net::ERR_INTERNET_DISCONNECTED"
A mock found a real bug. Run against ShopBot, both tests show that the product page gives the shopper no feedback at all when the API fails: the status line stays empty and a JavaScript error is logged. The tests above document today's behaviour; once the app is fixed, change them to expect a message such as "Something went wrong, please try again".

Slow responses and loading states

To test a spinner or a disabled button, the request has to stay pending while you assert. In the sync API the cleanest way is to hold the route and release it yourself (do not call time.sleep in a handler: it blocks the whole test thread).

from playwright.sync_api import Page, Route, expect


def test_message_waits_for_server(page: Page):
    held: list[Route] = []
    page.route("**/api/cart", lambda route: held.append(route))   # do not answer yet
    page.goto("/products/1")
    with page.expect_request("**/api/cart"):
        page.get_by_role("button", name="Add to cart").click()
    expect(page.get_by_role("status")).to_be_empty()       # still "loading"
    held[0].fulfill(json={"count": 1})                      # now let it finish
    expect(page.get_by_role("status")).to_have_text("Added to cart")
import asyncio
from playwright.async_api import Route


async def slow(route: Route):
    await asyncio.sleep(2)          # does not block other requests or the test
    await route.continue_()

await page.route("**/api/cart", slow)

cdp = page.context.new_cdp_session(page)

    "offline": False, "latency": 400,                      # ms added to every request

Blocking images, fonts and analytics

Blocking resources you do not test makes suites faster and stops tests from sending fake traffic to your analytics or advertising partners.

import re
from playwright.sync_api import Route

BLOCKED_TYPES = {"image", "font", "media"}


def block_heavy(route: Route):
    if route.request.resource_type in BLOCKED_TYPES:
        return route.abort()
    route.continue_()


page.route("**/*", block_heavy)                                   # by resource type
page.route("**/*.{png,jpg,jpeg,webp,svg}", lambda route: route.abort())   # or by extension
page.route(re.compile(r"(google-analytics|googletagmanager|segment)\.(com|io)"),
           lambda route: route.abort())                           # third-party trackers
# conftest.py: block trackers in every test
import pytest

@pytest.fixture(autouse=True)
def no_analytics(context):
    context.route(re.compile(r"(google-analytics|googletagmanager|segment)\.(com|io)"),
                  lambda route: route.abort())
Do not block images in tests that check layout or take screenshots, and remember that routing every request ("**/*") adds a little overhead to each one. A focused pattern is cheaper than a catch-all handler.

Waiting for and inspecting network traffic

Sometimes the thing to check is the request or response itself: the right payload was sent, the server answered 200, the analytics event fired. Start waiting before the action, inside a with block, so a fast response cannot be missed.

def test_add_to_cart_sends_quantity(page: Page):
    page.goto("/products/1")
    page.get_by_label("Quantity").fill("2")
    with page.expect_response("**/api/cart") as response_info:
        page.get_by_role("button", name="Add to cart").click()
    response = response_info.value
    assert response.ok
    assert response.request.method == "POST"
    assert response.request.post_data_json == {"product_id": 1, "qty": 2}
    assert response.json() == {"count": 2}


# a predicate for anything a glob cannot express
with page.expect_response(lambda r: r.url.endswith("/api/cart") and r.request.method == "POST") as info:
    page.get_by_role("button", name="Add to cart").click()

# the request only (does not wait for the response)
with page.expect_request("**/api/chat") as request_info:
    page.get_by_role("button", name="Send").click()
assert request_info.value.post_data_json == {"message": "How long is shipping?"}
# log all traffic while debugging
page.on("request", lambda r: print(">>", r.method, r.url))
page.on("response", lambda r: print("<<", r.status, r.url))
page.on("requestfailed", lambda r: print("xx", r.url, r.failure))
Prefer asserting on the UI (expect(...).to_have_text(...)) and use expect_response when the network behaviour is the requirement. Never replace either with page.wait_for_timeout(2000).

Record and replay traffic with HAR files

A HAR (HTTP Archive) file is a JSON recording of requests and responses. Playwright can record one while you run against the real back end, then replay it so later runs need no server for those URLs: realistic mocks without writing them by hand.

from playwright.sync_api import Browser, expect

HAR = "tests/hars/cart.har"

def record(browser: Browser):
    context = browser.new_context(base_url="http://127.0.0.1:8000")
    context.route_from_har(HAR, url="**/api/**", update=True)   # update=True: record
    page = context.new_page()
    page.goto("/products/1")
    page.get_by_role("button", name="Add to cart").click()
    expect(page.get_by_test_id("cart-count")).to_have_text("1")
    context.close()                       # the HAR file is written on close
def test_cart_from_har(context, page):
    context.route_from_har("tests/hars/cart.har", url="**/api/**", not_found="abort")
    page.goto("/products/1")              # the HTML still comes from the server
    with page.expect_response("**/api/cart") as info:
        page.get_by_role("button", name="Add to cart").click()
    assert info.value.json() == {"count": 1}          # served from the HAR
    expect(page.get_by_test_id("cart-count")).to_have_text("1")
# record everything a context does (not a route: requests still hit the server)
context = browser.new_context(
    record_har_path="session.har",
    record_har_url_filter="**/api/**",
    record_har_content="embed",          # "embed" bodies in the HAR, "attach" separate files, "omit"
)
# record by hand in a real browser window
playwright open --save-har=cart.har --save-har-glob="**/api/**" http://127.0.0.1:8000/products/1
  • Matching uses the URL and method, and for POST requests the body too: replaying the recording above, adding product 2 does not match the recorded request for product 1, so with not_found="abort" it fails (with "fallback" it goes to the network).
  • Commit HAR files next to the tests and re-record them when the API changes (run once with update=True). Scrub tokens, cookies and personal data before committing.
  • Use a url filter so the HAR stays small and only the API is replayed.

API testing with APIRequestContext

playwright.request.new_context() creates an HTTP client (no browser) with a base URL, default headers, a cookie jar and the same expect style. It is useful for testing the API on its own, for fast test set-up, and because API calls appear in Playwright traces next to the UI steps.

tests/conftest.py
import pytest
from playwright.sync_api import Playwright


@pytest.fixture(scope="session")
def api(playwright: Playwright, base_url: str):
    request = playwright.request.new_context(
        base_url=base_url,
        extra_http_headers={"Accept": "application/json"},
    )
    yield request
    request.dispose()

    response = api.post("/api/cart", data={"product_id": 2, "qty": qty})   # dict -> JSON body
    assert response.status == status, response.text()


def test_more_than_stock_is_rejected(api: APIRequestContext):
    response = api.post("/api/cart", data={"product_id": 2, "qty": 50})
    assert response.status == 422
    assert response.json() == {"detail": "Only 8 in stock"}

    assert response.status == 404

Why test the quantity rules through the API? The product page's input has max="8", so the browser refuses to submit 50 and the UI can never send it. The server must still reject it, because anyone can call the API directly. Validate at the API, check the user experience in the UI.

Cookies matter. An APIRequestContext keeps its own cookie jar. ShopBot only issues the sid session cookie on HTML pages, so call api.get("/") first if your test needs its own cart; without a cookie every cookieless client shares one anonymous cart, and counts leak between tests.

page.request: an API client that shares the browser's cookies

page.request (the same object as context.request) sends HTTP requests with the browser context's cookies, and cookies it receives are stored in the context. That is what makes it ideal for set-up: you act as the same user the browser is.

Who shares which cookie jar?

def test_api_and_browser_share_the_cart(page: Page):
    page.goto("/products")                                    # browser receives a sid cookie
    response = page.request.post("/api/cart", data={"product_id": 1, "qty": 3})
    assert response.json() == {"count": 3}
    page.goto("/cart")                                        # same cookie, same cart
    expect(page.get_by_test_id("cart-total")).to_have_text("£36.00")


def test_log_in_through_the_api(page: Page):
    page.request.post("/login", form={"email": "alice@example.com", "password": "wonderland"})
    page.goto("/account")                                     # already logged in
    expect(page.get_by_test_id("user-name")).to_have_text("Alice")

Combining API set-up with UI checks

The fastest reliable end-to-end tests build their starting state through the API and spend browser time only on the behaviour under test. Filling a cart through three product pages costs seconds and adds three places to fail; two API calls cost milliseconds.

tests/test_checkout.py
import re
from playwright.sync_api import Page, expect


def test_checkout_with_prepared_cart(page: Page):
    # Arrange through the API (shares the browser's cookies)
    page.goto("/products")
    page.request.post("/api/cart", data={"product_id": 2, "qty": 2})   # 2 x £39.50
    page.request.post("/api/cart", data={"product_id": 4, "qty": 1})   # 1 x £9.50

    # Act and assert in the UI
    page.goto("/cart")
    expect(page.get_by_role("row")).to_have_count(3)                  # header + 2 lines
    expect(page.get_by_test_id("cart-total")).to_have_text("£88.50")
    page.get_by_role("link", name="Checkout").click()
    page.get_by_label("Full name").fill("Alice Liddell")
    page.get_by_label("Email").fill("alice@example.com")
    page.get_by_label("Postcode").fill("OX1 1AA")
    page.get_by_label("I accept the terms").check()
    page.get_by_role("button", name="Place order").click()
    expect(page.get_by_role("status")).to_contain_text("confirmed")
    expect(page.get_by_test_id("order-id")).to_have_text(re.compile(r"^\d{6}$"))

The same idea works the other way round: do something in the UI, then verify the stored result through the API (for example, that an order really exists), and clean up test data through the API in a fixture's teardown.

Authentication: log in once, reuse the state

Logging in through the form in every test is slow and makes every test depend on the login page. Instead, log in once, save the context's storage state (cookies, localStorage and optionally IndexedDB) to a JSON file with context.storage_state(path=...), and start each test's context from that file with browser.new_context(storage_state=...). Each test still gets its own fresh context, so isolation is kept.

Logging in every test vs reusing storage_state

tests/conftest.py
import pytest

  • Treat state files as secrets: they contain live session cookies. Write them to a temporary directory (as above) or a git-ignored .auth/ folder, never commit them.
  • Session storage is not included. If your app keeps its token in sessionStorage, read it after login and restore it with context.add_init_script(...). Pass indexed_db=True to storage_state() for apps (such as some Firebase set-ups) that keep auth in IndexedDB.
  • Sessions expire. Create the state per test run (a session fixture) rather than reusing a file from yesterday.
  • Tests that change the account (log out, change password, delete) must not share the session with others: give them their own login.

Multiple roles

Real applications have customers, staff and administrators. Keep one account per role, log each role in once, and choose the role per test with a marker. pytest-playwright also ships a browser_context_args marker for one-off context options.

tests/conftest.py
import pytest
from playwright.sync_api import Playwright

# one account per role (ShopBot has one demo user; your app will have more)
ACCOUNTS = {
    "customer": {"email": "alice@example.com", "password": "wonderland"},
    # "admin":  {"email": "admin@example.com", "password": os.environ["ADMIN_PASSWORD"]},
}


def pytest_configure(config):
    config.addinivalue_line("markers", "as_user(role): run the test logged in as this role")


@pytest.fixture(scope="session")
def auth_state(playwright: Playwright, base_url: str, tmp_path_factory):
    cache: dict[str, str] = {}
    auth_dir = tmp_path_factory.mktemp("auth")

    def get(role: str) -> str:
        if role not in cache:                       # log in lazily, once per role
            path = auth_dir / f"{role}.json"
            request = playwright.request.new_context(base_url=base_url)
            request.get("/login")                   # get a session cookie first
            response = request.post("/login", form=ACCOUNTS[role])
            assert response.url.endswith("/account"), f"login failed for {role}"
            request.storage_state(path=path)
            request.dispose()
            cache[role] = str(path)
        return cache[role]

    return get


@pytest.fixture
def browser_context_args(browser_context_args, auth_state, request):
    marker = request.node.get_closest_marker("as_user")
    if marker is None:                              # no marker: anonymous visitor
        return browser_context_args
    return {**browser_context_args, "storage_state": auth_state(marker.args[0])}

Per-worker accounts for parallel runs

With pytest -n 4 (pytest-xdist) four processes run tests at the same time. If they all use one account, a test in worker 1 can empty the cart that worker 2 is checking. Read-only tests can share an account; tests that change server-side state need one account per worker. xdist's worker_id fixture is "gw0", "gw1", ... (or "master" without -n). 

import os
import pytest
from playwright.sync_api import Playwright


@pytest.fixture(scope="session")
def worker_account(worker_id: str) -> dict:
    # pre-created accounts qa-gw0@example.com, qa-gw1@example.com, ... (or create one via an admin API here)
    return {"email": f"qa-{worker_id}@example.com", "password": os.environ["QA_PASSWORD"]}


@pytest.fixture(scope="session")
def worker_state(playwright: Playwright, base_url: str, worker_account: dict, tmp_path_factory) -> str:
    path = tmp_path_factory.mktemp("auth") / "state.json"   # unique directory per worker
    request = playwright.request.new_context(base_url=base_url)
    request.get("/login")
    request.post("/login", form=worker_account)
    request.storage_state(path=path)
    request.dispose()
    return str(path)
pytest -n 4 --base-url http://127.0.0.1:8000

Session-scoped fixtures run once per worker under xdist, so each worker logs in once. If the login itself must happen only once for all workers, guard it with a file lock (the filelock package), as described in the pytest-xdist documentation.

WebSockets: observe and mock

Live stock levels, chat and notifications often use WebSockets. page.route_web_socket(url, handler) intercepts the connection; the handler receives a WebSocketRoute and can reply as a fake server, or connect to the real one and sit in the middle.

import json
from playwright.sync_api import Page, WebSocketRoute, expect


def test_live_stock_badge(page: Page):
    received = []

    def fake_stock_server(ws: WebSocketRoute):
        def on_message(message):
            received.append(message)
            if message == "subscribe:1":
                ws.send(json.dumps({"product_id": 1, "stock": 3}))
        ws.on_message(on_message)

    page.route_web_socket("wss://shopbot.example/ws/stock", fake_stock_server)
    page.goto("/products/1")          # a page that opens the socket and shows updates
    ...
    assert received == ["subscribe:1"]
def tamper(ws: WebSocketRoute):
    server = ws.connect_to_server()               # the real server connection

    def page_to_server(message):
        if message == "ping":
            ws.send("pong")                       # answer this one ourselves
        else:
            server.send(message)                  # forward everything else

    ws.on_message(page_to_server)
    server.on_message(lambda message: ws.send(message.replace("in stock", "LOW stock")))

page.route_web_socket("**/ws/stock", tamper)
# simulate the server dropping the connection
page.route_web_socket("**/ws/stock",
    lambda ws: ws.on_message(lambda m: ws.close(code=4001, reason="maintenance")))

# observe a real (not mocked) socket
with page.expect_websocket() as ws_info:
    page.goto("/live")
ws = ws_info.value
ws.on("framereceived", lambda payload: print("<<", payload))
ws.on("framesent", lambda payload: print(">>", payload))
  • ShopBot has no WebSocket endpoint; the fake-server and close examples were checked against a small page that opens wss://shopbot.example/ws/stock, which never exists on the network: the mock is the only server.
  • With route_web_socket and no connect_to_server(), the page never connects anywhere, and the page.on("websocket") / expect_websocket events are not fired for it. Use those events to observe real sockets.
  • Like page.route, the pattern can be relative: it is resolved against base_url with http changed to ws.

Server-sent events and streaming responses

AI chat UIs, including ShopBot's /chat, usually stream with server-sent events (SSE): a long HTTP response of data: ... lines. There is no special SSE API in Playwright, because SSE is just HTTP: you can mock it with route.fulfill and a text/event-stream body.

tests/test_chat_mocked.py
import json
from playwright.sync_api import Page, expect


def sse(*events: dict) -> str:
    return "".join(f"data: {json.dumps(e)}\n\n" for e in events)


def test_chat_shows_streamed_answer_and_sources(page: Page):
    body = sse(
        {"type": "token", "text": "Returns are free "},
        {"type": "token", "text": "within 30 days [returns]."},
        {"type": "done", "sources": ["returns"]},
    )
    page.route("**/api/chat", lambda route: route.fulfill(
        status=200, content_type="text/event-stream", body=body))
    page.goto("/chat")
    page.get_by_placeholder("Ask a question").fill("Can I return a mug?")
    page.get_by_role("button", name="Send").click()
    answer = page.get_by_test_id("bot-message")
    expect(answer).to_have_attribute("aria-busy", "false")     # stream finished
    expect(answer).to_have_text("Returns are free within 30 days [returns].")
    expect(answer).to_have_attribute("data-sources", "returns")
ConsiderationWhat to do
route.fulfill delivers the whole body at onceFine for testing parsing and the final state. To test timing (tokens appearing one by one, a "stop" button mid-stream), point the app at a fake streaming server or a fake LLM back end instead (see Testing AI applications).
route.fetch() waits for the complete responseDo not use fetch-and-modify on a long-lived stream; it would wait for the stream to end.
EventSource reconnects automaticallyA mocked response that ends will make a real EventSource reconnect after a few seconds; include a final event your UI treats as "done", or route.abort() the retry.
Waiting for "finished"Assert on a UI signal (aria-busy="false", a "done" attribute, the Send button re-enabled), not on the response event: for streams the response event fires when headers arrive.
Real model, real streamUse generous timeouts and assert on properties (cites a source, mentions "30 days"), not exact text. ShopBot's default fake LLM is deterministic for tests.

1. Empty search results easy

Without touching ShopBot's data, make /products show "No products found." by modifying the server's HTML response, and assert the result count text.

The product list is rendered on the server, so patch the HTML with route.fetch(). (The real way to get there is a search with no match, but this shows the technique.)

import re

def test_no_products(page: Page):
    def empty_grid(route):
        response = route.fetch()
        html = re.sub(r'<div class="grid">.*?</div></main>',
                      '<div class="grid"><p role="status">No products found.</p></div></main>',
                      response.text(), flags=re.S)
        route.fulfill(response=response, body=html)

    page.route("**/products", empty_grid)
    page.goto("/products")
    expect(page.get_by_role("status")).to_have_text("No products found.")
    expect(page.get_by_test_id("product-card")).to_have_count(0)

4. API-first stock rule medium

Write a parametrised API test proving that every product rejects a quantity one above its stock, using the stock values returned by GET /api/products. Skip products with no stock.

def products(api):
    return api.get("/api/products").json()

def test_stock_limit_for_every_product(api: APIRequestContext):
    for p in products(api):
        if p["stock"] == 0:
            continue
        r = api.post("/api/cart", data={"product_id": p["id"], "qty": p["stock"] + 1})
        assert r.status == 422, p["name"]

5. Fast logged-in cart test hard

Write a test that starts logged in as Alice (no login form), puts two notebooks in her cart through the API, and checks the cart page total. Then explain why the cart might already contain items when run twice.

def test_alice_cart(browser, base_url, alice_state):
    context = browser.new_context(base_url=base_url, storage_state=alice_state)
    page = context.new_page()
    page.request.post("/api/cart", data={"product_id": 4, "qty": 2})
    page.goto("/cart")
    expect(page.get_by_role("row", name="Notebook Set")).to_contain_text("£19.00")
    context.close()

The storage state holds one session (sid) for the whole run, and ShopBot keeps the cart on the server per session, so every test using alice_state shares one cart: if another test also added notebooks, the row would show more than £19.00. Fixes: empty the cart in a fixture before and after, compare against the count returned by the API call, or give tests that write their own login (a function-scoped state).
