Debugging, tracing, reporting and CI

A test suite is only as good as the speed at which you can understand a failure. Playwright gives you a debugger (the Inspector) for stepping through a test while you write it, verbose logs for "why did it wait?", and the trace viewer: a recording of every action with DOM snapshots before and after, network traffic, console output and the source line. A trace from a failed CI run lets you debug as if the failure had happened on your laptop.

This page covers those tools, the playwright trace command-line inspector (handy for terminals and coding agents), screenshots and videos, HTML and Allure reports, a practical guide to flaky tests, and running the suite in CI: GitHub Actions, Azure Pipelines, the official Docker image, sharding across machines and remote browsers. The examples test ShopBot at http://127.0.0.1:8000 (see the example app).

Playwright Inspector and page.pause()

The Inspector is a small window that opens next to a headed browser. It shows your test's Playwright calls, lets you step over them one by one or resume, highlights the element each locator resolves to, and has a Pick locator button that suggests a locator for anything you click on the page (the same engine as playwright codegen). You can also type a locator and see what it matches live.

tests/test_checkout.py
from playwright.sync_api import Page, expect


def test_checkout_needs_terms(page: Page):
    page.goto("/checkout")
    page.get_by_label("Full name").fill("Alice")
    page.pause()                     # opens the Inspector here; the browser stays open
    page.get_by_role("button", name="Place order").click()
    expect(page.get_by_role("alert")).to_contain_text("You must accept the terms")

page.pause() only makes sense in a headed run. Two ways to get the Inspector without editing code:

# headed + Inspector, timeouts disabled, paused before the first action (bash)
PWDEBUG=1 pytest tests/test_checkout.py -k terms

# PowerShell
$env:PWDEBUG = "1"; pytest tests/test_checkout.py -k terms

# headed, slowed down, no Inspector
pytest --headed --slowmo 500 tests/test_checkout.py

# PWDEBUG=console: headed, and a `playwright` helper object in the browser DevTools console
# (try playwright.$('text=Place order') or playwright.inspect('role=button'))
PWDEBUG=console pytest tests/test_checkout.py
Python debugger too. Playwright calls are ordinary Python: put breakpoint() in a test, or run pytest --pdb to drop into pdb on the first failure while the browser is still open. In VS Code or PyCharm, debug the test like any pytest test; add --headed to the run arguments. Remember that the default 30 s action timeout keeps ticking while you sit at a breakpoint; PWDEBUG=1 disables it.

Letting an agent (or you) drive a paused test from the terminal

pytest-playwright 0.10 adds --playwright-debug=cli: the test pauses before its first action and prints a session name that playwright cli (the terminal tool for coding agents) can attach to. You can then take accessibility snapshots, step over calls and resume, all from a shell. It needs -s (so the message is visible) and a single worker.

$ pytest -s --playwright-debug=cli tests/test_cart.py -k add
### The test is currently paused at the start

### Debugging Instructions
- Run `python -m playwright cli attach tw-11ebd2` to attach to this test

# in a second terminal (or from your coding agent)
$ python -m playwright cli attach tw-11ebd2
### Paused
- Navigate /products/1 at ./test_cart.py:4
$ python -m playwright cli -s=tw-11ebd2 step-over
### Paused
- Fill "2" get_by_label("Quantity") at ./test_cart.py:5
$ python -m playwright cli -s=tw-11ebd2 snapshot      # YAML accessibility snapshot with refs e1, e2...
$ python -m playwright cli -s=tw-11ebd2 resume        # the test runs to the end

The trace viewer

A trace is a zip file recorded during a test: the list of actions with timings and parameters, a DOM snapshot before, during and after each action (real HTML and CSS you can inspect, not just a picture), a screencast filmstrip, every network request and response, console messages, errors and the Python source line.

Recording traces with pytest

# keep a trace only for tests that failed (the usual CI setting)
pytest --tracing retain-on-failure

# record every test (slower, bigger; good when investigating)
pytest --tracing on

# the usual "give me everything on failure" combination
pytest --tracing retain-on-failure --screenshot only-on-failure --video retain-on-failure --output test-results

Artifacts go into one folder per test under --output (default test-results). This is the real layout for a failed test:

test-results/
└── tests-test-cart-py-test-add-nine-pans-chromium/   # <test file path>-<test name>-<browser>
    ├── trace.zip                                  # trace-1.zip, trace-2.zip if the test opened several contexts
    ├── test-failed-1.png                          # from --screenshot only-on-failure (one per page)
    └── video.webm                                 # from --video retain-on-failure (video-1.webm... per page)

Video needs Playwright's ffmpeg build. playwright install chromium normally fetches it; if you see "Video rendering requires ffmpeg binary", run playwright install ffmpeg.

Recording traces in a script (or your own fixture)

trace_search.py
from playwright.sync_api import sync_playwright, expect

with sync_playwright() as p:
    browser = p.chromium.launch()
    context = browser.new_context(base_url="http://127.0.0.1:8000")
    context.tracing.start(screenshots=True, snapshots=True, sources=True)
    page = context.new_page()
    try:
        with context.tracing.group("Search for a mug"):     # groups nest actions in the viewer
            page.goto("/products")
            page.get_by_placeholder("Search products").fill("mug")
            page.get_by_role("button", name="Search").click()
        expect(page.get_by_test_id("product-card")).to_have_count(1)
    finally:
        context.tracing.stop(path="trace-search.zip")         # always save, even on failure
        browser.close()

screenshots records the filmstrip, snapshots the DOM snapshots, sources embeds your Python files so the viewer can show the line. For long-lived contexts use tracing.start_chunk() / stop_chunk(path=...) to save one trace per step instead of one huge file.

Reading a trace: a real failure, step by step

This test expected ShopBot's "Only 8 in stock" message and timed out. The animation replays its real trace (timings from the recording). Watch the Network tab.

tests/test_cart.py
def test_add_nine_pans(page: Page):
    page.goto("/products/2")                                   # Cast Iron Pan, 8 in stock
    page.get_by_label("Quantity").fill("9")
    page.get_by_role("button", name="Add to cart").click()
    expect(page.get_by_role("status")).to_have_text("Only 8 in stock")

Mock trace viewer: actions, before/after snapshots, network and console

The diagnosis: the trace shows no POST /api/cart at all. The quantity input has max="8", so the browser's own form validation blocked the submit and the page's JavaScript never ran. The test's assumption ("the server will answer with an error") was wrong, not the app. Two better tests:

def test_quantity_above_stock_is_blocked_in_the_browser(page: Page):
    page.goto("/products/2")
    qty = page.get_by_label("Quantity")
    qty.fill("9")
    page.get_by_role("button", name="Add to cart").click()
    assert qty.evaluate("el => el.validity.rangeOverflow")     # "Value must be less than or equal to 8."
    expect(page.get_by_role("status")).to_be_empty()


def test_server_rejects_quantity_above_stock(page: Page):
    response = page.request.post("/api/cart", data={"product_id": 2, "qty": 9})
    assert response.status == 422
    assert response.json() == {"detail": "Only 8 in stock"}
Trace viewer areaWhat to look for
Actions list and timelineWhich step failed, how long each took; a 5 s bar is a timeout, a long gap between actions is your Python code (or a sleep)
Before / Action / After snapshotsThe page as it was: was the element there, covered, disabled, showing old data? The red dot marks the click point. Open DevTools on the snapshot.
Call logThe auto-waiting steps (same as DEBUG=pw:api): "locator resolved to ...", "unexpected value ..."
NetworkMissing requests, 4xx/5xx responses, slow APIs, which requests a page.route handled
Console and ErrorsJavaScript exceptions and console.error output from the page
SourceThe Python line for the selected action

Inspecting traces from the terminal: playwright trace

The trace viewer is a GUI. When you are in an SSH session, a CI log, or you want a coding agent to diagnose a failure, use playwright trace: it extracts the zip once (into .playwright-cli/ in the current folder; add it to .gitignore) and then answers questions about it as plain text.

CommandDoes
playwright trace open trace.zipExtract the trace and print a summary (browser, duration, counts of actions, requests, errors, console messages)
playwright trace actions [--grep TEXT] [--errors-only]Numbered list of actions with start time and duration; failures marked ✗
playwright trace action 4One action in detail: parameters, call log, error, source stack, which snapshots exist
playwright trace requests [--grep URL] [--method POST] [--status 500] [--failed]Network requests; playwright trace request 3 shows one in full
playwright trace console [--errors-only] [--warnings] [--browser] [--stdio]Console messages from the page and the test's stdout/stderr
playwright trace errorsErrors with their source location
playwright trace snapshot 4 --phase before|action|afterLoad that DOM snapshot in a headless browser and run a playwright cli command on it (default: print the accessibility snapshot); --serve serves it on localhost. Needs the bundled Chromium.
playwright trace screenshot 4 -o step4.pngSave the filmstrip frame for an action (an agent can look at it with vision)
playwright trace attachments / attachment 1 -o fileList and extract attachments
playwright trace closeDelete the extracted data
playwright trace install-skillWrite a SKILL.md describing these commands to .claude/skills/playwright-trace/ so a coding agent knows how to use them

Fail the test on JavaScript errors

A page can look fine while throwing exceptions. This fixture collects console.error messages and uncaught exceptions and fails the test at teardown (verified: the favicon 404 that ShopBot produces on every page is filtered out).

tests/conftest.py
import pytest
from playwright.sync_api import ConsoleMessage, Page

IGNORED = ("favicon.ico",)          # known, harmless noise


@pytest.fixture
def console_errors(page: Page):
    errors: list[str] = []

    def on_console(msg: ConsoleMessage) -> None:
        where = msg.location.get("url", "")
        if msg.type == "error" and not any(s in where for s in IGNORED):
            errors.append(f"console.error: {msg.text} ({where})")

    page.on("console", on_console)
    page.on("pageerror", lambda exc: errors.append(f"uncaught: {exc}"))
    yield errors
    assert not errors, "Browser errors during the test:\n" + "\n".join(errors)

Use it explicitly (def test_x(page, console_errors)) or make it autouse=True once your app is clean.

HTML reports and Allure

pytest-html

pip install pytest-html
pytest --html=report.html --self-contained-html --screenshot only-on-failure --tracing retain-on-failure

pytest-playwright 0.10 detects pytest-html and attaches its own artifacts to each failed test automatically: the screenshot and video (embedded with --self-contained-html, linked otherwise) and a Trace link to the zip. To add more context, append extras in a hook:

tests/conftest.py (optional extras)
import pytest


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when == "call" and report.failed and "page" in item.funcargs:
        html = item.config.pluginmanager.getplugin("html")
        if html:                                            # only when pytest-html is installed
            extras = getattr(report, "extras", [])
            extras.append(html.extras.url(item.funcargs["page"].url, name="Page URL at failure"))
            report.extras = extras

JUnit XML for CI dashboards

pytest --junitxml=results/junit.xml is understood by GitHub (via a reporting action), Azure Pipelines (PublishTestResults@2), GitLab and Jenkins, which then show test counts, failures and history per run.

Allure

Allure produces a richer report (steps, history, trends, categories) from result files. Install allure-pytest; the report itself is built by the Allure command-line tool (a separate install that needs Java).

allure serve allure-results            # or: allure generate allure-results -o allure-report
tests/conftest.py (Allure attachments)
import allure
import pytest


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when == "call" and report.failed and "page" in item.funcargs:
        page = item.funcargs["page"]
        allure.attach(page.screenshot(), name="screenshot", attachment_type=allure.attachment_type.PNG)
        allure.attach(page.content(), name="dom", attachment_type=allure.attachment_type.HTML)


# in tests: readable steps in the report
def test_search(page):

        page.goto("/products")
        page.get_by_placeholder("Search products").fill("mug")
        page.get_by_role("button", name="Search").click()

Attach the trace zip too (allure.attach.file(path, name="trace", extension="zip")) from a fixture that runs after pytest-playwright has written it, or simply publish test-results/ next to the report.

Diagnosing flaky tests

A flaky test passes and fails on the same code. Almost always the test is racing the application. The classic case on ShopBot: read the cart badge right after clicking "Add to cart". On a fast laptop the fetch has finished by the time Python reads the text; on a busy CI runner it has not. Switch the machine in the animation.

Racing the page: a one-shot read versus a retrying assertion

# flaky: inner_text() reads once, immediately
page.get_by_role("button", name="Add to cart").click()
assert page.get_by_test_id("cart-count").inner_text() == "1"

# stable: expect() retries until the text matches or the timeout expires
page.get_by_role("button", name="Add to cart").click()
expect(page.get_by_test_id("cart-count")).to_have_text("1")

# streaming chat: wait for the "done" state, then check the content
bot = page.get_by_test_id("bot-message").last
expect(bot).to_have_attribute("aria-busy", "false")
expect(bot).to_contain_text("3-5 business days")

Verified on ShopBot: the badge read passed 5 runs out of 5 locally (exactly why it slips through review) while the same one-shot read on the streaming chat answer failed every time with an empty string.

SymptomLikely causeFix
Passes locally, fails in CIOne-shot reads (inner_text(), is_visible(), count()) racing async updatesWeb-first assertions: expect(locator).to_have_text(...), to_be_visible(), to_have_count()
Fails at a fixed point after a time.sleep / wait_for_timeoutHard-coded waits that are too short on slow machines (and too long on fast ones)Wait for a condition: an assertion, page.expect_response(...), wait_for_url
Strict mode violation sometimesLocator matches several elements once more data loadsNarrow the locator (role + name, filter(has_text=), scope to a container)
Fails only when run with other tests or with -nShared state: same user, same cart, same database rows, order dependenceFresh data per test (API set-up, unique names), per-worker accounts, no module-level state
Fails near midnight, month end or in another time zoneReal clock and localepage.clock, fixed timezone_id and locale in browser_context_args
Random 5xx or timeouts from third partiesReal external services (payments, analytics, maps)Mock them with page.route; test the integration separately
Click "does nothing" occasionallyPage not hydrated yet, animations, overlays, element re-renderedAssert a ready state first (an element that appears after load), disable animations, check the trace snapshot
Screenshots differ by a few pixelsFonts, GPU, OS differences, animations, caretsRun visual tests in the Docker image, animations="disabled", masks, tolerance
Only the first test of a run failsServer not ready when tests startWait for a health endpoint in CI before running pytest

Tools for flaky tests

# reproduce: run one test many times, in parallel, with traces
pip install pytest-repeat
pytest tests/test_cart.py -k badge --count 30 -n 4 --tracing retain-on-failure

# re-run only what failed last time
pytest --last-failed

# quarantine while you fix it: retry up to 2 times (pytest-rerunfailures)
pytest --reruns 2 --reruns-delay 1
Retries hide problems. Reruns keep the pipeline green but a test that needs a retry is still broken. Report reruns (the summary line shows "rerun"), keep a trace of the first failure, track a flaky list and fix the top offenders. Mark known-flaky tests with @pytest.mark.flaky(reruns=2) rather than retrying everything.

CI with GitHub Actions

The pipeline below checks out the code, installs Python dependencies (with pip caching), installs Chromium and its Linux system libraries, starts the app, runs the suite in parallel with xdist on three machines, and always uploads the results so failures can be debugged from their traces.

A pull request through the pipeline

.github/workflows/e2e.yml
name: e2e
on:
  pull_request:
  push:
    branches: [main]

jobs:
  e2e:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    strategy:
      fail-fast: false                  # let every shard finish so you see all failures
      matrix:
        group: [1, 2, 3]                # three machines (see "Sharding")
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: "3.13"
          cache: pip                    # caches pip downloads, keyed on requirements*.txt

      - name: Install Python dependencies
        run: pip install -r requirements.txt      # pins playwright==1.64.1, pytest-playwright, pytest-xdist, pytest-split...

      - name: Cache Playwright browsers
        id: pw-cache
        uses: actions/cache@v5
        with:
          path: ~/.cache/ms-playwright
          key: pw-${{ runner.os }}-${{ hashFiles('requirements.txt') }}
      - name: Install browsers and system dependencies
        if: steps.pw-cache.outputs.cache-hit != 'true'
        run: python -m playwright install --with-deps chromium
      - name: Install system dependencies only
        if: steps.pw-cache.outputs.cache-hit == 'true'
        run: python -m playwright install-deps chromium

      - name: Start ShopBot
        run: |
          python app.py &
          curl --retry 30 --retry-connrefused --retry-delay 1 -sf http://127.0.0.1:8000/health

      - name: Run tests
        run: >
          pytest -n auto
          --splits 3 --group ${{ matrix.group }}
          --base-url http://127.0.0.1:8000
          --tracing retain-on-failure --screenshot only-on-failure --video retain-on-failure
          --junitxml=results/junit-${{ matrix.group }}.xml
          --html=results/report-${{ matrix.group }}.html --self-contained-html

      - name: Upload results and traces
        uses: actions/upload-artifact@v5
        if: ${{ !cancelled() }}         # also when tests failed
        with:
          name: e2e-results-${{ matrix.group }}
          path: |
            results/
            test-results/
          retention-days: 14
  • Caching: pip caching is cheap and worth it. Caching the browsers is optional: the official CI guide notes that restoring the cache takes about as long as downloading, and the Linux system packages cannot be cached, which is why the cache-hit branch still runs install-deps. Key the cache on the file that pins the Playwright version.
  • Install only what you test: playwright install --with-deps chromium is much faster than all three browsers.
  • Wait for the app: the curl --retry loop avoids "first test fails" flakiness.
  • Artifacts: download the zip from the run page and open a trace with playwright show-trace, or let an agent read it with playwright trace.
  • Versions: the action versions shown are those in the Playwright CI guide at the time of writing; newer majors exist, so update them as you would any dependency.

CI with Azure Pipelines

azure-pipelines.yml
trigger:
  - main
pr:
  - main

jobs:
  - job: e2e
    pool:
      vmImage: ubuntu-latest
    strategy:
      parallel: 3                       # three agents; each gets System.JobPositionInPhase = 1..3
    timeoutInMinutes: 30
    steps:
      - task: UsePythonVersion@0
        inputs:
          versionSpec: "3.13"
        displayName: Use Python

      - script: pip install -r requirements.txt
        displayName: Install dependencies

      - script: python -m playwright install --with-deps chromium
        displayName: Install Playwright browsers

      - script: |
          python app.py &
          curl --retry 30 --retry-connrefused --retry-delay 1 -sf http://127.0.0.1:8000/health
        displayName: Start ShopBot

      - script: >
          pytest -n auto
          --splits $(System.TotalJobsInPhase) --group $(System.JobPositionInPhase)
          --base-url http://127.0.0.1:8000
          --tracing retain-on-failure --screenshot only-on-failure
          --junitxml=results/junit.xml
        displayName: Run tests

      - task: PublishTestResults@2
        condition: succeededOrFailed()
        inputs:
          testResultsFormat: JUnit
          testResultsFiles: results/junit.xml
          testRunTitle: e2e shard $(System.JobPositionInPhase)

      - task: PublishPipelineArtifact@1
        condition: failed()             # test-results/ only exists when something failed
        inputs:
          targetPath: test-results
          artifact: traces-$(System.JobPositionInPhase)

The Tests tab of the run then shows every test with its history, and the traces are on the Artifacts page. To run in the Playwright container instead of installing browsers, add container: mcr.microsoft.com/playwright/python:v1.64.1-noble to the job and drop the install step.

The official Docker image

Microsoft publishes images with Python, the browsers and all their system libraries already installed. Tags follow v<playwright version>-<Ubuntu codename>: -noble (Ubuntu 24.04), -jammy (22.04) and -resolute (26.04).

Match the image to your installed Playwright version. The image contains the browser builds for exactly one Playwright release; the playwright package itself is not preinstalled. Pin playwright==1.64.1 in requirements.txt and use mcr.microsoft.com/playwright/python:v1.64.1-noble. If the versions differ, tests fail with "Executable doesn't exist". Upgrade both together.
# run the suite in the image against your working copy
docker run --rm -it --ipc=host --init -v "$PWD":/work -w /work \
  mcr.microsoft.com/playwright/python:v1.64.1-noble \
  sh -c "pip install -r requirements.txt && pytest -n auto --tracing retain-on-failure"
Dockerfile
FROM mcr.microsoft.com/playwright/python:v1.64.1-noble
WORKDIR /work
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt      # playwright==1.64.1 to match the tag
COPY . .
CMD ["pytest", "-n", "auto", "--tracing", "retain-on-failure"]
  • --ipc=host: Chromium uses shared memory and can crash without it. --init: avoids zombie processes (PID 1 handling).
  • The image runs as root by default, which disables Chromium's sandbox. That is acceptable for your own end-to-end tests; for crawling untrusted sites run as the built-in pwuser with the seccomp profile from the Docker guide.
  • From inside a container, 127.0.0.1 is the container. Reach an app on the host with --add-host=hostmachine:host-gateway and --base-url http://hostmachine:8000, or run the app in the same compose network.
  • Running visual comparisons inside the same image locally and in CI removes most font and rendering differences.

Sharding across CI machines

xdist (-n auto) parallelises inside one machine. When the suite is still too slow, split it across machines (shards) and run xdist on each. pytest has no built-in sharding; common options:

ApproachHowNotes
pytest-split (by duration)pytest --store-durations once (commits .test_durations), then pytest --splits 3 --group 1 on machine 1, and so onBalanced shards; new tests without a recorded duration get the average. Refresh the durations file occasionally.
Markerspytest -m smoke, -m "checkout or cart", -m "not slow" in separate jobsSimple and explicit; shards get unbalanced as the suite grows
Folderspytest tests/shop, pytest tests/accountSame trade-off as markers
BrowsersOne job per --browser chromium|firefox|webkitA natural matrix axis, combinable with the others
$ pytest --store-durations                     # writes .test_durations
$ pytest --splits 3 --group 2 -n auto
[pytest-split] Running group 2/3 (estimated duration: 8.07s)

Give each shard's artifacts a unique name (e2e-results-${{ matrix.group }} above) and, if you want one report, merge the JUnit files in a final job (most CI test tabs already aggregate them for you).

Remote browsers and cloud grids

Tests can drive a browser running somewhere else. There are two protocols:

browser_type.connect(ws_endpoint)chromium.connect_over_cdp(endpoint_url)
Talks toA Playwright server (playwright run-server, the Docker image, cloud providers)Any Chromium-based browser exposing the Chrome DevTools Protocol
BrowsersChromium, Firefox, WebKitChromium, Chrome, Edge only
FidelityFull Playwright featuresLower: some features behave differently; best for attaching to an existing browser
VersionsClient and server must be the same Playwright versionAny reasonably recent Chrome
Typical useA browser farm, a Linux container from a Windows laptop, cloud gridsAttaching to a user's signed-in browser, Electron apps, browsers started by other tools

A Playwright server and the pytest fixture override

# on the browser machine (or in the Docker image; same Playwright version as the tests)
playwright run-server --port 3000 --host 0.0.0.0
tests/conftest.py
import os

import pytest
from playwright.sync_api import BrowserType


@pytest.fixture(scope="session")
def browser(browser_type: BrowserType):
    """Use a remote browser when PW_WS_ENDPOINT is set, e.g. ws://grid.internal:3000/"""
    endpoint = os.environ.get("PW_WS_ENDPOINT")
    if not endpoint:
        browser = browser_type.launch()                 # local fallback
    else:
        browser = browser_type.connect(endpoint, timeout=30_000)
    yield browser
    browser.close()

All the other fixtures (context, page, tracing, screenshots) keep working, because they build on browser. Note that the browser runs on the remote machine, so --base-url must be reachable from there (not 127.0.0.1 of your laptop), and launch options come from the server side.

Attaching over CDP

# Chrome started with:  chrome --remote-debugging-port=9222 --user-data-dir=C:\temp\pw-profile
# (recent Chrome versions refuse remote debugging on the default profile)
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.connect_over_cdp("http://127.0.0.1:9222")
    context = browser.contexts[0]                     # the existing default context
    page = context.pages[0] if context.pages else context.new_page()
    page.goto("http://127.0.0.1:8000/products")
    print(page.title())                               # Products - ShopBot
    browser.close()                                   # disconnects; it does not kill the user's Chrome

Cloud grids

Commercial grids (BrowserStack, LambdaTest, Sauce Labs and similar) and Microsoft's hosted Playwright browsers on Azure give you many browsers and operating systems on demand. For Python they generally work through connect with a wss:// URL that carries your credentials and the requested browser and OS, which fits the fixture override above. Follow each provider's Python instructions; keep credentials in CI secrets; check which Playwright versions they support (the version must match); and expect higher latency, so rely on web-first assertions rather than tight timeouts. Playwright also has an experimental Selenium Grid integration (SELENIUM_REMOTE_URL, Chromium only).

Common mistakes

  • Committing page.pause(): a headless CI run with a pause hangs until the job timeout. Search for it in code review (or a pre-commit grep).
  • Not uploading artifacts when tests fail: the upload step must run on failure (if: ${{ !cancelled() }}, condition: succeededOrFailed()), otherwise the traces vanish exactly when you need them.
  • Tracing everything in CI by default: --tracing on slows runs and fills storage; use retain-on-failure.
  • Docker tag and pip version out of step: v1.63.0-noble with playwright 1.64.1 gives "Executable doesn't exist". Pin and bump both.
  • Forgetting --with-deps on Linux: the browser downloads, then fails to start with missing shared libraries.
  • Fixing flakiness with sleeps or retries: replace one-shot reads with expect, and treat reruns as a quarantine, not a cure.
  • Using 127.0.0.1 from a container or remote browser: it points at the container or the remote machine, not your app.
  • Ignoring the call log: the assertion error already says what the locator resolved to and the value it saw; read it before opening the debugger.
  • Committing .playwright-cli/ or test-results/: add both to .gitignore.

# tests/test_checkout_trace.py
from playwright.sync_api import Page, expect

def test_checkout_wrong_expectation(page: Page):
    page.goto("/checkout")
    page.get_by_label("Full name").fill("Alice")
    page.get_by_role("button", name="Place order").click()

Make a flaky test stable easy

This test passes on your laptop but fails in CI about one run in ten. Explain why and fix it.

def test_add_two_mugs(page):
    page.goto("/products/1")
    page.get_by_label("Quantity").fill("2")
    page.get_by_role("button", name="Add to cart").click()
    time.sleep(0.2)
    assert page.locator("#msg").inner_text() == "Added to cart"
    assert page.get_by_test_id("cart-count").inner_text() == "2"

The message and badge are updated after an asynchronous fetch. 200 ms is usually enough locally but not on a loaded runner, and inner_text() reads once. Remove the sleep and use retrying assertions (and a role-based locator):

def test_add_two_mugs(page):
    page.goto("/products/1")
    page.get_by_label("Quantity").fill("2")
    page.get_by_role("button", name="Add to cart").click()
    expect(page.get_by_role("status")).to_have_text("Added to cart")
    expect(page.get_by_test_id("cart-count")).to_have_text("2")
Fail tests on uncaught page errors, but only for some tests medium

Using the console_errors fixture idea, make it automatic for every test, with a marker @pytest.mark.allow_console_errors to opt out.

# conftest.py
import pytest

def pytest_configure(config):
    config.addinivalue_line("markers", "allow_console_errors: do not fail on browser errors")

@pytest.fixture(autouse=True)
def _fail_on_page_errors(request, page):
    errors = []
    page.on("pageerror", lambda exc: errors.append(str(exc)))
    page.on("console", lambda m: errors.append(m.text)
            if m.type == "error" and "favicon.ico" not in m.location.get("url", "") else None)
    yield
    if errors and not request.node.get_closest_marker("allow_console_errors"):
        pytest.fail("Browser errors:\n" + "\n".join(errors))

Note this autouse fixture requests page, so every test gets a browser page; put it in the conftest.py of your UI test folder only, not next to pure API tests.

Add a browser matrix to the GitHub Actions workflow medium

Extend the workflow so pull requests run Chromium on three shards, and a nightly schedule also runs Firefox and WebKit.

on:
  pull_request:
  schedule:
    - cron: "0 2 * * *"

jobs:
  e2e:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        browser: ${{ github.event_name == 'schedule' && fromJSON('["chromium","firefox","webkit"]') || fromJSON('["chromium"]') }}
        group: [1, 2, 3]
    steps:
      # ... checkout, setup-python, pip install as before ...
      - run: python -m playwright install --with-deps ${{ matrix.browser }}
      - run: pytest -n auto --browser ${{ matrix.browser }} --splits 3 --group ${{ matrix.group }} --tracing retain-on-failure
      - uses: actions/upload-artifact@v5
        if: ${{ !cancelled() }}
        with:
          name: results-${{ matrix.browser }}-${{ matrix.group }}
          path: test-results/

Write a failure-summary script for a triage agent hard

Write a Python script that finds every trace.zip under test-results/ and prints, for each, the failed actions, failed requests and console errors, using the playwright trace CLI. Its output will be pasted into an LLM prompt.

# summarise_traces.py
import subprocess
import sys
from pathlib import Path

def trace(*args: str) -> str:
    out = subprocess.run([sys.executable, "-m", "playwright", "trace", *args],
                         capture_output=True, text=True, encoding="utf-8")
    return (out.stdout + out.stderr).strip()

def main(root: str = "test-results") -> None:
    sys.stdout.reconfigure(encoding="utf-8")       # the output contains symbols such as ✗ (matters on Windows)
    zips = sorted(Path(root).rglob("trace*.zip"))
    if not zips:
        print("No traces: nothing failed.")
        return
    for z in zips:
        print(f"## {z.parent.name}")
        trace("open", str(z))
        for title, args in [("Failed actions", ["actions", "--errors-only"]),
                            ("Errors", ["errors"]),
                            ("Failed requests", ["requests", "--failed"]),
                            ("Console errors", ["console", "--errors-only"])]:
            print(f"### {title}\n{trace(*args) or '(none)'}\n")
        trace("close")

if __name__ == "__main__":
    main(*sys.argv[1:])

Keep the summary short (it is untrusted page output: treat it as data in the prompt, never as instructions), and attach trace screenshot N images if the model supports vision.
