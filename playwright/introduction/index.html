What Playwright is and how it works

Playwright is an open-source browser automation library from Microsoft. From a Python program you launch a real browser (Chromium, Firefox or WebKit), open pages, click, type, read the page and check what it shows, exactly like a user would, only faster and repeatably. It is used mostly for end-to-end (E2E) testing of web applications, but also for scraping, robotic process automation, screenshots and PDFs, monitoring, and as the browser that AI agents use to act on the web.

This page explains where Playwright came from, the problems it solves, the three objects you will use in every script (browser, context, page), how it compares with Selenium, Cypress and Puppeteer, when it is the wrong tool, and how a typical Python test project is laid out.

What Playwright is

Playwright gives you one API to control three browser engines:

EngineBrowsers built on itHow Playwright gets it
ChromiumGoogle Chrome, Microsoft Edge, Opera, BraveDownloads a pinned Chromium build (playwright install chromium) or drives your installed Chrome / Edge with channel="chrome" / "msedge"
FirefoxMozilla FirefoxDownloads a lightly patched Firefox build
WebKitApple Safari (macOS and iOS)Downloads a WebKit build, so you can test Safari-like behaviour on Windows and Linux

Around that core you get the things a test suite needs: auto-waiting (actions wait until the element is ready), web-first assertions that retry, user-facing locators such as get_by_role("button", name="Search"), network interception, isolated browser contexts, device emulation, a trace viewer for debugging, a code generator, and a pytest plugin (pytest-playwright).

from playwright.sync_api import sync_playwright, expect

with sync_playwright() as p:                      # starts the Playwright driver
    browser = p.chromium.launch()                 # one browser process (headless by default)
    page = browser.new_page()                     # a tab in a fresh, isolated context
    page.goto("http://127.0.0.1:8000/products")
    page.get_by_role("link", name="Ceramic Mug").click()
    expect(page.get_by_role("heading", level=1)).to_have_text("Ceramic Mug")
    browser.close()

A short history

WhenWhat happened
2017Google's Chrome team releases Puppeteer, a Node.js library for driving Chrome through the Chrome DevTools Protocol (CDP). It shows how fast and reliable protocol-level automation can be, but it is Chrome-only and JavaScript-only.
2019Several of the engineers behind Puppeteer move to Microsoft and start a new project with a broader goal: every engine, every language, built for testing.
January 2020Playwright is released as open source (Node.js) with Chromium, Firefox and WebKit support from day one.
2020Version 1.0. Playwright for Python appears the same year (pip install playwright), followed by Java and .NET. All of them share one driver, so features land in every language at once.
2021The trace viewer arrives, and the pytest-playwright plugin becomes the standard way to write Python tests. (Node gets its own test runner, Playwright Test.)
2022The "locators first" API: get_by_role, get_by_label, get_by_text, get_by_test_id and friends become the recommended way to find elements.
2024 - 2025ARIA snapshots (to_match_aria_snapshot), and the Playwright MCP server, which lets LLM agents drive a browser through the accessibility tree.
2026Release 1.64 (used on these pages). The Python package ships the MCP server (playwright mcp) and agent-friendly CLIs (playwright cli, playwright trace).

Playwright ships a new minor version roughly every month. Each release pins specific browser builds, which is why you re-run playwright install after upgrading.

Why it exists

Before Playwright, most browser tests used Selenium WebDriver. Selenium is a W3C standard and is still widely used, but test suites built in the 2010s were famous for being flaky: they passed and failed at random. The common causes:

The Selenium-era problems

  • No built-in waiting. You had to add WebDriverWait (or worse, time.sleep(2)) before every interaction. Too short is flaky, too long is slow.
  • Stale elements. You held a reference to a DOM node; the page re-rendered; you got StaleElementReferenceException.
  • Covered elements. A click landed on a spinner or cookie banner instead of the button ("element click intercepted").
  • Heavy set-up. Separate driver binaries per browser version, Selenium Grid for parallelism, a fresh browser per test for isolation.
  • Little control of the network. Mocking an API or simulating an error needed a proxy.

What modern web apps need

  • Single-page apps that render asynchronously, stream data, and change the DOM constantly.
  • Shadow DOM (web components), iframes, multiple tabs and pop-ups, file uploads and downloads.
  • Testing on Safari's engine without owning a Mac farm.
  • Fast, isolated tests that can run in parallel on a CI machine.
  • Tools to understand failures after the fact (traces, videos, screenshots).

Playwright's answer: locators are lazy and re-resolved on every use (no stale elements), every action waits for the element to be visible, stable, enabled and not covered, assertions retry until the page reaches the expected state, browser contexts give each test a clean profile in milliseconds, and the driver talks to the browsers over fast bidirectional protocols, so it can also intercept network traffic and listen to events.

Core concepts: browser, context, page

Every Playwright program works with the same hierarchy. Learn these three objects and the rest of the API falls into place.

ObjectWhat it isCostTypical lifetime
BrowserOne running browser process (Chromium, Firefox or WebKit), started with p.chromium.launch()Expensive: hundreds of milliseconds to start, tens of MB of memoryThe whole test session
BrowserContextAn isolated, incognito-like profile inside the browser: its own cookies, local storage, cache, permissions, viewport, locale, time zone and network routesCheap: a few millisecondsOne test (or one user in a multi-user test)
PageA single tab (or pop-up window) inside a context. You navigate, find elements and act through itCheapOne test, or as long as the tab is open

Pages in the same context share cookies (like two tabs of the same browser window). Pages in different contexts share nothing, even though they run in one browser process. That is how one test can log in as Alice while another runs as a guest, in parallel, without interfering. Step through the animation.

One browser, two isolated contexts

from playwright.sync_api import sync_playwright, expect

with sync_playwright() as p:
    browser = p.chromium.launch()
    alice = browser.new_context()                 # profile 1
    page_a = alice.new_page()
    page_a.goto("http://127.0.0.1:8000/login")
    page_a.get_by_label("Email").fill("alice@example.com")
    page_a.get_by_label("Password").fill("wonderland")
    page_a.get_by_role("button", name="Log in").click()
    expect(page_a.get_by_test_id("user-name")).to_have_text("Alice")

    tab2 = alice.new_page()                       # same context: shares Alice's cookie
    tab2.goto("http://127.0.0.1:8000/account")
    expect(tab2.get_by_test_id("user-name")).to_have_text("Alice")

    guest = browser.new_context()                 # profile 2: empty cookie jar
    page_g = guest.new_page()
    page_g.goto("http://127.0.0.1:8000/account")  # not logged in, so ShopBot redirects
    expect(page_g).to_have_url("http://127.0.0.1:8000/login")
    browser.close()
Tip. browser.new_page() is a shortcut that creates a new context with one page in it. It is fine for scripts; in tests, the pytest plugin gives you a fresh context and page per test automatically.

One driver, many languages

The Python package contains a small driver (a bundled Node.js program). Your Python code sends it JSON messages over a pipe; the driver speaks each browser's protocol. The Node.js, Java and .NET packages use the same driver, which is why the APIs are almost identical across languages (Python uses snake_case: get_by_role, to_have_text). What happens during a pytest-playwright run

Two consequences worth knowing early:

  • The sync API is a thin wrapper. playwright.sync_api runs an event loop internally (using greenlets), so you cannot call it from inside asyncio code such as a Jupyter cell or a FastAPI handler. Use playwright.async_api there.
  • The browser builds are pinned to the package version. Upgrading playwright means running playwright install again.

When not to use Playwright

SituationWhy Playwright is the wrong toolUse instead
Testing a Python function or classA browser adds seconds and flakiness to something that needs microsecondsPlain pytest unit tests
Load or stress testing (1000s of users)Each browser uses a CPU core and hundreds of MB; you would measure your test machine, not the serverLocust, k6, JMeter (and a handful of Playwright journeys for client-side timings)
Native mobile or desktop appsPlaywright drives web pages, not native UI widgets. Device emulation is a desktop browser pretending to be a phoneAppium, platform UI test frameworks, real-device clouds
Certifying real Safari on iPhoneWebKit is Safari's engine, not Safari itself (no Apple-specific features or real device quirks)Real devices or a device cloud; keep Playwright WebKit for fast feedback
Scraping static HTML or a JSON APIA browser is slower and heavier than an HTTP requesthttpx / requests + an HTML parser
Checking every edge case of business logic through the UIUI tests are the slowest, most expensive layer; hundreds of them make CI slowAPI and unit tests for the logic; a few E2E tests for the critical journeys
Bypassing CAPTCHAs, bot protection or a site's termsAutomation does not give you permissionAn official API, or ask the owner

How a test project is laid out

A Playwright test project in Python is an ordinary pytest project. A typical layout (you will build it on the next page):

shopbot-e2e/
├── pyproject.toml          # dependencies + [tool.pytest.ini_options] (base URL, browser, tracing)
├── .venv/                  # virtual environment (not committed)
├── tests/
│   ├── conftest.py         # shared fixtures: context options, logged-in page, test data
│   ├── test_search.py      # one file per feature or user journey
│   ├── test_cart.py
│   └── test_checkout.py
├── pages/                  # optional page objects (see the pytest page)
│   ├── __init__.py
│   └── products_page.py
├── test-results/           # traces, screenshots, videos written by pytest-playwright (not committed)
└── .github/workflows/e2e.yml   # CI job (see the debugging and CI page)
PieceRole
pytest-playwrightThe pytest plugin: provides the browser, context and page fixtures and the --browser, --headed, --base-url, --tracing options
conftest.pyWhere you customise fixtures, for example browser_context_args to set viewport and locale for every test
test_*.pyTest functions that take page as an argument, act, and assert with expect
test-results/Per-test output folder (traces you open with playwright show-trace)

Common misconceptions

  • "Playwright is a test runner." In Python it is a library. pytest is the runner; pytest-playwright connects the two. The Node.js "Playwright Test" runner, its config file and its UI mode are not part of the Python package.
  • "WebKit means Safari." It is the same engine, good for catching most Safari bugs, but not the shipping Safari app.
  • "One new browser per test is safest." A new context gives the same isolation and is far cheaper.
  • "Headless behaves differently, so always test headed." Headless is the normal mode for CI; use headed (--headed) for watching and debugging.
  • "Auto-waiting means I never need to think about timing." It removes most waits, but you still have to assert on the right outcome (for example wait for the confirmation text, not for an arbitrary time).
  • "Playwright can test anything with a UI." Only web content (and Electron, from Node). Native apps need other tools.

Exercises

Two tests run in parallel against ShopBot: one logs in as Alice and adds a mug to the cart, the other checks that a guest's cart is empty. Should they share a browser? A context?

They can share a browser (one process, cheap to reuse) but each needs its own context. Contexts do not share cookies, so the guest test never sees Alice's session cookie or her cart. This is exactly what pytest-playwright does: the browser fixture is session-scoped, context and page are created per test.

Your team must prove that checkout works in Safari on iPhones. Is Playwright WebKit enough?

It is a good, fast first line of defence (same engine, emulated iPhone viewport and user agent with p.devices["iPhone 15"]), but it is not Safari on a real iPhone. For a sign-off, add a small set of runs on real devices or a device cloud. Keep the bulk of the suite in Playwright for speed.

Pick the right tool: (a) check that /api/products returns four products, (b) check that 2,000 simultaneous users can search, (c) check that the search page works in Firefox.

(a) An API test (Playwright's page.request/APIRequestContext or httpx), no browser needed. (b) A load-testing tool such as Locust or k6. (c) A Playwright E2E test with pytest --browser firefox.

Write a script that opens ShopBot's products page in two contexts, one with the viewport of an iPhone 15 and one with a 1280 × 800 desktop viewport, and prints the viewport size of each page. 
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    phone = browser.new_context(**p.devices["iPhone 15"])
    desktop = browser.new_context(viewport={"width": 1280, "height": 800})
    for ctx in (phone, desktop):
        page = ctx.new_page()
        page.goto("http://127.0.0.1:8000/products")
        print(page.viewport_size)       # {'width': 393, 'height': 659} then {'width': 1280, 'height': 800}
    browser.close()
Why can Playwright's Python, Java and .NET packages add a new feature in the same release?

All language packages are thin clients over the same driver, which contains the real automation logic (waiting, selectors, protocol handling). A feature implemented in the driver only needs a small binding in each language.
