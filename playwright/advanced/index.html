Advanced browser features

The earlier pages covered the everyday core: locators, actions, assertions, fixtures, network mocking and CI. This page is the toolbox for everything else a real application throws at you: phones and tablets, other languages and time zones, dark mode and offline mode, timers that would take minutes to fire, new tabs, iframes, browser dialogs, file uploads and downloads, running your own JavaScript in the page, visual regression, accessibility and performance checks, and tests in which two users talk to each other.

Every Python snippet below was run against ShopBot with Playwright for Python 1.64 and pytest-playwright 0.10 (Chromium). Where ShopBot has no matching feature (timers, a two-user chat), the snippet uses a tiny inline page or says clearly which page your own app would need.

Device and environment emulation

A browser context carries the whole "environment" of a simulated user: screen size, pixel density, touch support, user agent, language, time zone, location, permissions, colour scheme and network state. You set it when you create the context, so each test can be a different kind of user without restarting the browser.

Emulation playground: pick a user, see the code and what the page sees

The price and date are formatted live by your browser's Intl API with the chosen locale and time zone, exactly what page JavaScript would get inside the emulated context. (ShopBot itself formats prices on the server, so its pages always show pounds.)

from playwright.sync_api import Browser, Playwright, expect


def test_products_on_an_iphone(browser: Browser, playwright: Playwright):
    iphone = playwright.devices["iPhone 15"]        # viewport, user agent, scale factor, touch, is_mobile

    assert page.viewport_size == {"width": 393, "height": 659}
    assert page.evaluate("() => document.documentElement.scrollWidth <= window.innerWidth")   # no sideways scroll

Mobile and touch

A device descriptor turns on has_touch, so you can use tap(). Without touch support, tap() fails with "The page does not support tap. Use hasTouch context option to enable touch support."

import re

def test_tap_through_to_product(browser, playwright):
    context = browser.new_context(**playwright.devices["Pixel 7"], base_url="http://127.0.0.1:8000")
    page = context.new_page()
    page.goto("/products")
    page.get_by_role("link", name="Ceramic Mug").tap()              # a touch tap, not a mouse click
    expect(page).to_have_url(re.compile(r"/products/1$"))

    box = page.get_by_role("button", name="Add to cart").bounding_box()
    page.touchscreen.tap(box["x"] + box["width"] / 2, box["y"] + box["height"] / 2)   # tap at coordinates
    expect(page.get_by_role("status")).to_have_text("Added to cart")
    context.close()

Controlling time: the clock API

Session time-outs, "sale ends in 10:00" banners, auto-save every 30 seconds, "posted 2 hours ago" labels and calendars that change at midnight are hard to test against the real clock. page.clock replaces the page's Date, setTimeout, setInterval, requestAnimationFrame, performance.now() and friends with a fake clock that your test controls. ShopBot has no timers, so this example uses a small inline page with a session warning after 14 minutes.

Fake time: a 14-minute session warning tested in milliseconds

import datetime as dt
from playwright.sync_api import Page, expect

SESSION_PAGE = """
<p>Time: <span id="now"></span></p>
<p id="warn" role="alert"></p>
<script>
  const show = () => document.getElementById('now').textContent = new Date().toISOString().slice(11, 19);
  show();
  setInterval(show, 1000);
  setTimeout(() => document.getElementById('warn').textContent = 'Your session expires in 1 minute', 14 * 60 * 1000);
</script>
"""


def test_session_warning_after_14_minutes(page: Page):
    page.clock.install(time=dt.datetime(2026, 12, 24, 9, 0, tzinfo=dt.timezone.utc))   # BEFORE the page loads
    page.set_content(SESSION_PAGE)                    # in your app: page.goto("/account")
    page.clock.pause_at(dt.datetime(2026, 12, 24, 9, 0, 5, tzinfo=dt.timezone.utc))
    expect(page.locator("#now")).to_have_text("09:00:05")

    page.clock.run_for(3000)                          # every timer due in the next 3 s fires, in order
    expect(page.locator("#now")).to_have_text("09:00:08")
    expect(page.get_by_role("alert")).to_have_text("")

    page.clock.fast_forward("14:00")                  # jump 14 minutes ("mm:ss" or milliseconds)
    expect(page.get_by_role("alert")).to_have_text("Your session expires in 1 minute")
    expect(page.locator("#now")).to_have_text("09:14:08")
MethodWhat it doesUse it for
clock.install(time=...)Installs fake timers starting at time. Time keeps flowing normally until you pause it. Call it before the page's scripts run.Every timer test; it must come first
clock.pause_at(time)Jumps to time like fast_forward (due timers fire once) and stops there. It works before or after the page loads. The time must be in the future, otherwise: "Cannot fast-forward to the past".Deterministic tests: nothing moves unless you say so
clock.run_for(ms | "mm:ss")Advances step by step, firing every timer that falls due, in order (an interval of 1 s fires 10 times in 10 s)Animations, polling, counters
clock.fast_forward(ms | "mm:ss")Jumps ahead; each due timer fires at most once, at the new time (like a laptop waking from sleep). Verified: 10 ticks, then a 60 s fast-forward gives 11, not 70.Time-outs, expiry, "come back later"
clock.resume()Lets time flow again from where it isFinishing a test with normal behaviour

clock.set_system_time(time)Changes the wall clock without firing timers (after install)Simulating the user changing the system clock, DST jumps

Pass time-zone-aware datetimes (tzinfo=dt.timezone.utc) or ISO strings ending in Z. A naive datetime is interpreted in the test machine's local time zone, so a test written in London fails on a CI runner in UTC half the year. Combine with timezone_id= on the context to control how the page displays it.

Multiple pages, tabs and popups

Every tab or window is a Page in the same context (they share cookies). When a click opens a new tab (target="_blank", window.open), wrap the click in page.expect_popup(): Playwright starts listening before the click, so the event cannot be missed. ShopBot's home page has a "Terms (opens a new tab)" link: 

def test_terms_open_in_a_new_tab(page):
    page.goto("http://127.0.0.1:8000/")
    with page.expect_popup() as popup_info:
        page.get_by_role("link", name="Terms (opens a new tab)").click()
    terms = popup_info.value                         # the new Page
    terms.wait_for_load_state()
    expect(terms).to_have_title("Terms - ShopBot")
    expect(terms.get_by_role("heading", level=1)).to_have_text("Terms and conditions")
    assert len(page.context.pages) == 2

    terms.close()
    expect(page.get_by_role("heading", level=1)).to_have_text("Welcome to ShopBot")   # the first tab is untouched

iframes

An iframe is a separate document, so normal locators do not see inside it. ShopBot's account page embeds a "Loyalty card" iframe with a points balance and a Redeem button. frame_locator() (or locator.content_frame) gives you a locator scope inside the frame, with the same auto-waiting as everywhere else. 

def test_redeem_loyalty_points(logged_in_page):          # a fixture that logs in as alice (see the pytest page)
    page = logged_in_page
    page.goto("/account")

    card = page.frame_locator('iframe[title="Loyalty card"]')
    expect(card.locator("#points")).to_have_text("120")
    card.get_by_role("button", name="Redeem").click()
    expect(card.locator("#points")).to_have_text("0")


def test_same_with_content_frame(logged_in_page):
    page = logged_in_page
    page.goto("/account")
    card = page.get_by_title("Loyalty card").content_frame   # locator for the <iframe> -> its content
    expect(card.get_by_text("Loyalty points")).to_be_visible()
  • Nested frames: chain them, page.frame_locator("#outer").frame_locator("#inner").get_by_role(...).
  • The Frame object (page.frames, page.frame(name=...), page.frame(url=...)) is the older, non-locator API. Prefer locators; use Frame when you need frame-level calls such as frame.evaluate() or frame.url.
  • Cross-origin iframes (payment widgets, embedded videos) work the same way: Playwright drives them through the browser, not through page JavaScript, so the same-origin policy does not block you.

Dialogs: alert, confirm, prompt, beforeunload

Native dialogs block the page until someone answers. By default Playwright dismisses them automatically (so a confirm returns false). To answer one, register a handler before the action that opens it. ShopBot's "Delete account" button asks "Really delete your account? This cannot be undone." 

def test_cancel_account_deletion(logged_in_page):
    page = logged_in_page
    page.goto("/account")
    page.once("dialog", lambda dialog: dialog.dismiss())      # press "Cancel"
    page.get_by_role("button", name="Delete account").click()
    expect(page.locator("#delete-msg")).to_have_text("Deletion cancelled")


def test_confirm_account_deletion(logged_in_page):
    page = logged_in_page
    page.goto("/account")
    seen = []

    def handle(dialog):
        seen.append((dialog.type, dialog.message))            # record; assert outside the handler
        dialog.accept()                                       # press "OK"; for a prompt: dialog.accept("Alice")

    page.once("dialog", handle)
    page.get_by_role("button", name="Delete account").click()
    expect(page.locator("#delete-msg")).to_have_text("Account scheduled for deletion")
    assert seen == [("confirm", "Really delete your account? This cannot be undone.")]
Handle every dialog you listen for. If you register page.on("dialog", ...) and the handler neither accepts nor dismisses, the page stays frozen and the click hangs until it times out. Use page.once for a single dialog, and do assertions after the action, not inside the handler (an exception raised inside an event handler does not fail the test cleanly). beforeunload dialogs only appear with page.close(run_before_unload=True).

Running JavaScript: evaluate, add_init_script, expose_function

Sometimes you need to reach inside the page: read a value the UI does not show, prepare state before the app starts, or let page code call back into Python.

    clicks = []
    page.expose_function("reportClick", lambda label: clicks.append(label))
    page.add_init_script("""

Do not use evaluate to act. page.evaluate("document.querySelector('button').click()") skips every actionability check: it "clicks" hidden, disabled or covered buttons that a real user could not, so the test passes while the feature is broken. Act with locators; use evaluate to read or to prepare.

Visual regression testing in Python

Functional assertions do not notice that the Checkout button turned white on white or that the product grid collapsed into one column. A visual regression test takes a screenshot, compares it with an approved baseline image, and fails when too many pixels differ. The Node test runner has toHaveScreenshot; Python has no built-in equivalent, so you either write a small helper with Pillow (below, about 40 lines) or use a community plugin.

Pixel diff: thresholds, masks and noise

tests/conftest.py (visual helper)
from io import BytesIO
from pathlib import Path

import pytest
from PIL import Image, ImageChops

BASELINE_DIR = Path(__file__).parent / "__screenshots__"      # commit these PNGs


def pytest_addoption(parser):
    parser.addoption("--update-baselines", action="store_true", help="Rewrite visual baselines")


@pytest.fixture
def assert_screenshot(request, output_path):                   # output_path: pytest-playwright's per-test folder
    update = request.config.getoption("--update-baselines")

    def check(target, name, *, mask=(), pixel_threshold=24, max_diff_ratio=0.001):
        png = target.screenshot(animations="disabled", caret="hide", mask=list(mask))   # page or locator
        actual = Image.open(BytesIO(png)).convert("RGB")
        baseline_path = BASELINE_DIR / f"{name}.png"

        if update or not baseline_path.exists():
            baseline_path.parent.mkdir(parents=True, exist_ok=True)
            actual.save(baseline_path)
            if not update:
                pytest.fail(f"No baseline for {name!r}: created {baseline_path}. Review it, commit it, re-run.")
            return

        expected = Image.open(baseline_path).convert("RGB")
        if expected.size != actual.size:
            pytest.fail(f"{name}: size changed {expected.size} -> {actual.size}")

        diff = ImageChops.difference(expected, actual).convert("L")      # 0..255 per pixel
        changed = diff.point(lambda v: 255 if v > pixel_threshold else 0)
        n_changed = changed.histogram()[255]
        ratio = n_changed / (actual.width * actual.height)
        if ratio > max_diff_ratio:
            out = Path(output_path)                                       # test-results/<test-id>/
            out.mkdir(parents=True, exist_ok=True)
            actual.save(out / f"{name}-actual.png")
            overlay = actual.copy()
            overlay.paste((255, 0, 0), mask=changed)                     # changed pixels in red
            overlay.save(out / f"{name}-diff.png")
            pytest.fail(f"{name}: {n_changed} pixels differ ({ratio:.3%} > {max_diff_ratio:.3%}). "
                        f"See {out}. If the change is intended, run with --update-baselines.")

    return check

The baseline workflow

# 1. first run: no baseline yet, so the helper saves one and fails on purpose
pytest tests/visual
#    Failed: No baseline for 'products': created tests/__screenshots__/products.png. Review it, commit it, re-run.

# 2. later runs compare; a real change fails with a diff image
#    Failed: products: 1359 pixels differ (0.147% > 0.100%). See test-results/test-visual-py-test-products-page-chromium.

# 3. the change was intended (a redesign): accept it, review the PNG diff in the pull request
pytest tests/visual --update-baselines
git add tests/__screenshots__ && git commit -m "Update visual baselines for new header"
  • Generate baselines where the tests run. Fonts, anti-aliasing and GPU rendering differ between Windows, macOS and Linux. Create and compare baselines in the same Docker image as CI (see Debugging and CI), one set per browser.
  • Remove what legitimately changes: mask=[locator, ...] paints a box over dynamic parts (dates, counters, ads, avatars); style="..." injects CSS during the screenshot (visibility: hidden on a carousel); page.clock.set_fixed_time(...) freezes dates; mock API data with page.route.
  • Remove motion: animations="disabled" finishes finite CSS animations and transitions and cancels infinite ones; caret="hide" (the default) hides the text cursor.
  • Prefer component screenshots (locator.screenshot()) over full pages: smaller diffs, fewer unrelated failures, clearer ownership.
  • Plugins if you would rather not maintain a helper: pytest-playwright-visual-snapshot provides an assert_snapshot(page) fixture with a pixelmatch comparison, an --update-snapshots flag, and ini settings for threshold and global masks. Hosted services (Percy, Applitools, Chromatic, Argos and similar) add review UIs and smarter, perceptual comparison.

Accessibility testing

Accessible pages are better for everyone, are a legal requirement in many places, and, as a bonus, are exactly what makes role-based locators and AI agents work well. Playwright offers two complementary tools: ARIA snapshots (assert on the accessibility tree that screen readers see) and axe-core scans (automatic rule checks such as missing labels, alt text and contrast).

ARIA snapshots

locator.aria_snapshot() returns the accessibility tree as YAML. This is the real output for ShopBot's search form:

print(page.get_by_role("search").aria_snapshot())

- search:
  - text: Search
  - textbox "Search":
    - /placeholder: Search products
  - text: Category
  - combobox "Category":
    - option "All" [selected]
    - option "Kitchen"
    - option "Office"
  - button "Search"

expect(...).to_match_aria_snapshot() compares against a template. Matching is partial: you list only what matters, children in order, and attributes or text you omit are ignored. Values in /slashes/ are regular expressions.

def test_search_form_structure(page):
    page.goto("/products")
    expect(page.get_by_role("search")).to_match_aria_snapshot("""
      - search:
        - textbox "Search"
        - combobox "Category":
          - option "All" [selected]
          - option "Kitchen"
          - option "Office"
        - button "Search"
    """)


def test_results_structure(page):
    page.goto("/products?q=mug")
    expect(page.get_by_role("main")).to_match_aria_snapshot("""
      - heading "Products" [level=1]
      - paragraph: /\\d+ results?/
      - article:
        - heading "Ceramic Mug" [level=2]
    """)

An ARIA snapshot test fails if someone replaces the <button> with a clickable <div>, removes a label or breaks heading levels, even if the page still looks identical. aria_snapshot(mode="ai") adds element refs like [ref=f1e5], the format AI agents use (see Playwright for AI agents).

Performance measurements

Playwright is not a load-testing tool (use Locust or k6 for that) and not a full audit tool (use Lighthouse), but a real browser is the right place to measure what one user experiences: page load timings, web vitals, request timings, and the effect of a slow network or CPU. 

def test_products_page_load_budget(page):
    page.goto("/products")
    nav = page.evaluate("() => performance.getEntriesByType('navigation')[0].toJSON()")
    timings = {
        "ttfb_ms": nav["responseStart"] - nav["requestStart"],     # server think time + network
        "dom_content_loaded_ms": nav["domContentLoadedEventEnd"],  # relative to navigation start
        "load_ms": nav["loadEventEnd"],
        "transfer_bytes": nav["transferSize"],
    }
    print(timings)    # e.g. {'ttfb_ms': 3.8, 'dom_content_loaded_ms': 17, 'load_ms': 46.9, 'transfer_bytes': 2267}
    assert timings["load_ms"] < 3000
VITALS = """
window.__vitals = {lcp: 0, cls: 0};
new PerformanceObserver(list => {
  for (const e of list.getEntries()) window.__vitals.lcp = e.startTime;
}).observe({type: 'largest-contentful-paint', buffered: true});
new PerformanceObserver(list => {
  for (const e of list.getEntries()) if (!e.hadRecentInput) window.__vitals.cls += e.value;
}).observe({type: 'layout-shift', buffered: true});
"""

def test_web_vitals(page):
    page.add_init_script(VITALS)                  # observers exist before the page paints
    page.goto("/products")
    page.wait_for_load_state("load")
    vitals = page.evaluate("window.__vitals")     # e.g. {'lcp': 92, 'cls': 0}
    assert vitals["lcp"] < 2500                   # "good" LCP threshold
    assert vitals["cls"] < 0.1                    # "good" CLS threshold

These observers are supported in Chromium-based browsers. INP needs real interactions; for the full set inject Google's web-vitals library with add_script_tag and report values through expose_function.

Browser timings are noisy. Keep performance checks in a separate, clearly marked job (@pytest.mark.perf), take the median of several runs, use generous budgets that catch regressions (a 3x slowdown) rather than tiny ones, and record the numbers over time rather than only pass/fail.

Several users in one test

Some features only exist between people: chat, comments, shared documents, "someone else just bought the last one", admin approves what a customer submitted. Because contexts are isolated (own cookies, storage and cache), one browser with two contexts is two users, cheaply, in the same test.

Two contexts, two users, one conversation

ShopBot's own chat is with a bot, so first a check ShopBot can do: two shoppers in one test never share a cart.

def test_carts_are_isolated_between_users(browser):

    guest_ctx = browser.new_context(base_url="http://127.0.0.1:8000")
    alice, guest = alice_ctx.new_page(), guest_ctx.new_page()

    alice, bob = two_users
    alice.goto("/messages/order-1042")
    bob.goto("/messages/order-1042")

    alice.get_by_role("textbox", name="Message").fill("Is the mug dishwasher safe?")
    alice.get_by_role("button", name="Send").click()
    expect(bob.get_by_test_id("message").last).to_have_text("alice: Is the mug dishwasher safe?")

    bob.get_by_role("textbox", name="Message").fill("Yes, it is.")
    bob.get_by_role("button", name="Send").click()
    expect(alice.get_by_test_id("message").last).to_have_text("bob: Yes, it is.")
    expect(alice.get_by_test_id("message")).to_have_count(2)

The storage_state files come from logging each user in once (see reusing login state). This pattern was verified against a small two-user chat app with exactly this markup. Note get_by_role("textbox", name="Message"): get_by_label("Message") would also match the list labelled "Messages" (label matching is a case-insensitive substring by default) and fail with a strict-mode violation.

  • Two contexts, not two pages. Two pages in one context share cookies, so they are the same user in two tabs (useful for testing "logged out in the other tab").
  • Mixed roles: an admin context approves a review that a customer context submitted, then the customer context sees it published.
  • Different devices: browser.new_context(**playwright.devices["iPhone 15"], storage_state=...) for one of them.
  • Different browsers in one test need two Browser objects (for example playwright.firefox.launch()); usually not worth it.

2. A "sale ends" countdown medium

A banner counts down from 10:00 and then shows "Sale over". Using the inline page below, check the text after 3 seconds and after 10 minutes without waiting.

SALE = """<p id="left"></p><script>
  const end = Date.now() + 10 * 60 * 1000, el = document.getElementById('left');
  const tick = () => { const s = Math.max(0, Math.round((end - Date.now()) / 1000));
    el.textContent = s ? `${Math.floor(s / 60)}:${String(s % 60).padStart(2, '0')} left` : 'Sale over'; };
  tick(); setInterval(tick, 1000);
</script>"""

def test_sale_countdown(page):
    page.clock.install(time="2026-11-27T07:59:00Z")
    page.clock.pause_at("2026-11-27T08:00:00Z")       # frozen BEFORE the page loads
    page.set_content(SALE)                            # so end is exactly 08:10:00
    expect(page.locator("#left")).to_have_text("10:00 left")
    page.clock.run_for(3000)
    expect(page.locator("#left")).to_have_text("9:57 left")
    page.clock.fast_forward("10:00")
    expect(page.locator("#left")).to_have_text("Sale over")

Pausing before the page loads matters here. If you load first and pause afterwards, the page computes end from a moment that depends on how long loading took, and the text after run_for is sometimes 9:56 and sometimes 9:57: a flaky test made of fake time.
