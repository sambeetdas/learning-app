← All topicsNext: CDN →

What is DNS and why does it exist?

Computers talk to each other using IP addresses (203.0.113.10, 2001:db8::1), but people remember names (example.com). DNS is the distributed, hierarchical database that turns names into the data needed to reach a service: mostly IP addresses, but also mail servers, verification tokens, security policies and more.

It is often called "the phone book of the internet", but a better picture is a delegated directory: no single server knows everything. Each level knows only who is responsible for the level below, and every answer can be cached for a stated time. That design is why DNS has scaled from a few thousand hosts to billions of names.

IdeaIn one line
HierarchyRoot → top-level domain (.com) → your domain (example.com) → your hosts (www).
DelegationEach level points to the servers responsible for the next one (NS records).
CachingEvery answer carries a TTL; resolvers, operating systems and browsers reuse it until it expires.
RedundancyEvery zone has several name servers, spread out using anycast.

How a lookup works (step through it)

You type www.example.com. The browser and OS check their own caches first. On a miss, the stub resolver asks the configured recursive resolver, which then does the walk. Use the stepper to see the full path, and how caching shortens it.

Resolution stepper

Browser/OS            Recursive resolver        Root        .com TLD        example.com NS
   | www.example.com? ---> |                       |              |                |
   |                       | www.example.com? ---> |              |                |
   |                       | <--- "ask .com servers"              |                |
   |                       | www.example.com? -------------->    |                |
   |                       | <--- "ask ns1.example.net" ---------|                |
   |                       | www.example.com? --------------------------------->  |
   |                       | <--- A 203.0.113.10, TTL 300 ---------------------- |
   | <--- 203.0.113.10 ----|   (cached for 300 s)

Details worth knowing

  • Recursive vs iterative: the client-to-resolver hop is recursive ("get me the final answer"); the resolver-to-server hops are iterative ("tell me who to ask next").
  • Glue records: if example.com is served by ns1.example.com, the TLD must also hand out that server's IP, otherwise resolving the name server would require resolving the domain it serves. These IPs are "glue".
  • CNAME chains: if www is an alias to d123.cdn.net, the resolver restarts the walk for the target name. Long chains add latency.
  • Query minimization: modern resolvers send only the part of the name each server needs (the root sees .com, not the full hostname), which improves privacy.
  • Cost: a cold lookup can take 100 ms or more; a cached one takes about a millisecond. Most lookups on a busy resolver are cache hits.

Caching and TTL

Caching is what makes DNS fast and cheap, and also what makes changes slow to spread. Every record carries a TTL (time to live, in seconds). Anyone who has the answer may reuse it for that long without asking again.

Cache layerNotes
BrowserKeeps its own short cache (Chrome: chrome://net-internals/#dns). Often caps long TTLs.
Operating systemStub resolver cache plus the hosts file, which wins over DNS. Clear with ipconfig /flushdns on Windows.
Recursive resolverThe big one: one resolver serves thousands of users, so most queries never reach the authoritative servers.
Application / runtimeSome runtimes cache forever or per connection (older JVM settings, long-lived connection pools, sidecars). A common cause of "we changed DNS but traffic still goes to the old server".

Low TTL (30-300 s)

  • Changes and failover take effect quickly.
  • Good for records behind health checks or during a migration.
  • More queries to your authoritative servers and slightly slower lookups.

High TTL (1-24 h)

  • Fewer queries, faster lookups, less cost.
  • More resilient: cached answers survive a short outage of your DNS provider.
  • A wrong record lives for hours and you cannot recall it.

Migration playbook

  1. Days ahead: lower the TTL of the records you will change (for example from 1 h to 60 s).
  2. Wait at least the old TTL so every cache has picked up the short one.
  3. Make the change. Watch traffic on both old and new targets.
  4. When stable, raise the TTL back.

Keep the old target running until its traffic is gone: some clients and resolvers ignore TTLs.

Negative caching: "this name does not exist" (NXDOMAIN) is cached too, for the time given in the zone's SOA record. If you query a name before creating it, you may keep seeing "not found" for a while after you add it.

                                      |  PoP 1   PoP 2   PoP 3  ...      |

                                                         | zone data

                                              | (API, IaC, database) |

Authoritative side

  • Use at least two name servers, ideally in different networks. Managed providers give you four or more, each reachable at many locations.
  • Anycast: the same IP is announced from many locations; routing sends each client to the nearest one. This cuts latency and absorbs DDoS attacks, because the traffic is spread across many sites.
  • Zone data flow: primary/secondary replication with AXFR/IXFR zone transfers, or (more common now) a provider API fed by infrastructure-as-code (Terraform, Bicep, CloudFormation, ExternalDNS).
  • Multi-provider DNS: publishing the same zone at two independent providers protects you from a provider outage (see the 2016 Dyn attack). Costs: keeping zones in sync and not using provider-specific features such as alias records or traffic policies.
  • Dynamic answers: geo, latency, weighted and health-checked routing are computed by the authoritative server at query time. The resolver caches the result, so keep these TTLs short.

Resolver side

  • Where it runs: ISP, public (Google, Cloudflare, Quad9), or your own (corporate Active Directory DNS, Unbound, BIND, CoreDNS, cloud VPC resolvers such as Azure DNS Private Resolver or Route 53 Resolver).
  • Forwarding: internal resolvers forward corp.example.com to internal servers and everything else to the internet, using conditional forwarders or private zones.
  • EDNS Client Subnet (ECS): lets a public resolver tell the authoritative server roughly where the user is, so a CDN or geo-routing can pick a nearby endpoint. It improves accuracy and leaks a bit of location, so some resolvers disable it.
  • Serve-stale: a resolver may answer from an expired cache entry when the authoritative servers are unreachable (RFC 8767). A helpful safety net.

Transport

  • UDP port 53 for most queries. Responses too large for UDP fall back to TCP port 53 (EDNS0 allows larger UDP messages; around 1232 bytes is the recommended safe size). Firewalls that block TCP/53 cause strange failures with DNSSEC and big answers.
  • Encrypted DNS hides queries from the local network: DoT (DNS over TLS, port 853), DoH (DNS over HTTPS, port 443, blends in with web traffic) and DoQ (over QUIC). They protect the client-to-resolver hop only; the resolver still sees your queries.
  • Enterprises often disable browser DoH so internal names and security filtering keep working.

DNS-based load balancing: what it can and cannot do

Good

  • Works with any client and any protocol; no proxy in the data path.
  • Global: can direct users to the nearest or healthiest region.
  • Cheap and simple to operate.

Not so good

  • Failover speed is limited by TTL and by clients that cache too long.
  • Resolver caching spreads load unevenly (one resolver = many users).
  • It sees the resolver's location (unless ECS), not the user's.
  • No awareness of per-request load or session state. Use a real load balancer behind each address.

Security

  • Cache poisoning: an attacker tricks a resolver into caching a forged answer. Defenses: random source ports and query IDs, DNSSEC validation, 0x20 case randomization.
  • DNSSEC: zones are signed (RRSIG), keys are published (DNSKEY), and the parent zone vouches for the child with a DS record, forming a chain of trust up to the root. It proves an answer is authentic and unmodified; it does not encrypt anything and does not hide queries. Needs careful key rollover.
  • DDoS: DNS is a prime target (the 2016 Mirai attack on Dyn took down many big sites that depended on one provider). Use anycast providers and consider a second provider. Open recursive resolvers can be abused for amplification attacks; never expose yours to the internet.
  • Dangling records / subdomain takeover: a CNAME pointing at a deleted cloud resource (storage bucket, app service, CDN endpoint) can be claimed by an attacker, who then serves content under your domain. Remove DNS records when you delete the resource, and audit regularly.
  • Domain hijacking: protect the registrar account with MFA, enable registrar lock, and restrict who can change NS records.
  • DNS tunneling and exfiltration: data hidden in queries to an attacker-owned domain. Monitor for unusual query volume, long or high-entropy names, and heavy TXT usage.
  • Privacy: plain DNS is visible to anyone on the path. Use DoT/DoH and pick a resolver whose logging policy you trust.
  • Email spoofing: publish SPF, DKIM and DMARC.

Design checklist and pitfalls

  • "It's always DNS": when everything looks healthy but nothing connects, check DNS first. Names that fail to resolve, stale caches and wrong search domains cause a large share of outages.
  • CNAME at the apex: not allowed. Use your provider's alias/flattening feature or the HTTPS record.
  • Search domains and ndots: in Kubernetes the default ndots:5 makes a lookup of api.example.com try several suffixes first. Use a trailing dot (api.example.com.) or lower ndots for services making many external calls, and run node-local DNS caching.
  • Application caching: long-lived processes may cache IPs forever. Set sane DNS TTL behavior in the runtime and re-resolve on connection failure.
  • Dual stack: if you publish AAAA, make sure IPv6 really works. Clients using "Happy Eyeballs" (RFC 8305) race IPv4 and IPv6 to hide small problems, but broken IPv6 still wastes time.
  • Low TTL is not instant failover: some resolvers and clients ignore it. Pair DNS failover with health checks and keep the old endpoint alive for a while.
  • Treat DNS as code: keep zones in version control, review changes, and avoid hand edits in a console. A typo in an NS or MX record can take down a whole domain.
  • Monitor: resolution success and latency from several locations, expiring domains and certificates, unexpected record changes, and query volume.
  • Reverse DNS: only the owner of the IP block (your ISP or cloud provider) can set PTR records.

Troubleshooting commands

# Windows (PowerShell)
Resolve-DnsName www.example.com                       # uses the system resolver
Resolve-DnsName www.example.com -Server 1.1.1.1 -Type A
Resolve-DnsName example.com -Type MX
Clear-DnsClientCache                                   # same as: ipconfig /flushdns
Get-DnsClientCache | Where-Object Name -like '*example*'

# nslookup (everywhere)
nslookup -type=NS example.com
nslookup www.example.com 8.8.8.8

# dig (Linux/macOS, or WSL)
dig www.example.com                # answer, TTL, which server answered
dig +trace www.example.com         # walk root -> TLD -> authoritative yourself
dig example.com NS +short
dig @ns1.example.net www.example.com   # ask the authoritative server directly (bypasses caches)
dig example.com DNSKEY +dnssec         # check DNSSEC data
dig -x 203.0.113.10                    # reverse lookup
  • Answer differs between resolvers? Compare an authoritative answer with a public resolver's: if they differ, it is a cache or propagation issue.
  • NXDOMAIN means the name does not exist; SERVFAIL means the resolver could not get a valid answer (often a broken delegation or DNSSEC problem); REFUSED means the server will not answer you.
  • "DNS propagation" is mostly just caches expiring. It takes about as long as the old TTL.

Quick reference

  • Pointing a name at a server: A/AAAA. At a hostname you do not control: CNAME (alias at the apex).
  • Need a fast switch: lower the TTL ahead of time, then change.
  • Need resilience: several name servers, anycast, optionally two providers.
  • Need to prove a domain is yours or authorize something: TXT.
  • Need host+port discovery: SRV.
  • Need tamper protection: DNSSEC. Privacy: DoT/DoH.
