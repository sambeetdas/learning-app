Why sorting matters

Sorting puts items in order. It is one of the most studied problems in computer science because so much else becomes easy once data is sorted: binary search, finding duplicates, merging, medians and percentiles, grouping, range queries, and greedy algorithms. Databases sort for ORDER BY, joins and index builds; every language ships a highly tuned sort.

PropertyMeaning
StableEqual keys keep their original relative order. Needed when sorting by several keys in turn (sort by name, then stably by department).
In placeUses O(1) (or O(log n)) extra memory.
AdaptiveFaster on input that is already partly sorted.
OnlineCan sort items as they arrive (insertion sort).
Comparison-basedOnly uses "is a < b?". Any such sort needs Ω(n log n) comparisons in the worst case: there are n! possible orders, and each comparison at best halves them, so you need log₂(n!) ≈ n log n comparisons.
Non-comparisonCounting, radix and bucket sort use the values themselves (digits, ranges) and can beat n log n for suitable data.

The algorithms explained

Insertion sort

Like sorting playing cards in your hand: take the next card and slide it left past bigger cards. Each item moves at most as far as it is out of place, so nearly sorted input takes almost linear time.

for i = 1 .. n-1:
    key = a[i];  j = i - 1
    while j ≥ 0 and a[j] > key:  a[j+1] = a[j];  j = j - 1
    a[j+1] = key

Merge sort (divide and conquer)

Split the array in half, sort each half recursively, then merge two sorted lists by repeatedly taking the smaller front element. T(n) = 2T(n/2) + O(n) = O(n log n), in every case.

def merge_sort(a):
    if len(a) <= 1: return a
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]: out.append(left[i]); i += 1     # <= keeps it stable
        else: out.append(right[j]); j += 1
    return out + left[i:] + right[j:]

Merging is the basis of external sorting (data larger than memory), parallel sorting and counting inversions.

Quick sort (divide and conquer)

Pick a pivot, partition so smaller items go left and larger right, then sort both sides recursively. No merging needed: after partitioning, the pivot is in its final place.

import random
def quick_sort(a, lo=0, hi=None):
    if hi is None: hi = len(a) - 1
    if lo >= hi: return
    r = random.randint(lo, hi); a[r], a[hi] = a[hi], a[r]     # random pivot avoids the O(n^2) trap
    p, i = a[hi], lo
    for j in range(lo, hi):
        if a[j] < p: a[i], a[j] = a[j], a[i]; i += 1
    a[i], a[hi] = a[hi], a[i]
    quick_sort(a, lo, i - 1); quick_sort(a, i + 1, hi)
  • Pivot choice: first/last element degrades to O(n²) on sorted input; random or median-of-three makes that astronomically unlikely.
  • Hoare partition (two pointers moving inwards) does fewer swaps than Lomuto. Three-way partition (<, =, >) handles many duplicates in linear time.
  • Why it is fast: tight inner loop, sequential memory access, in place. Recurse on the smaller side first to keep the stack O(log n).

Heap sort

Build a max-heap in O(n), then n times swap the root (maximum) to the end and sift down. Guaranteed O(n log n) with O(1) extra memory, but it jumps around memory, so it is usually slower than quicksort in practice. See heaps.

Counting, radix and bucket sort (non-comparison)

def counting_sort(a, k):                  # values in 0..k, stable version
    count = [0] * (k + 1)
    for x in a: count[x] += 1
    for v in range(1, k + 1): count[v] += count[v - 1]      # prefix sums = end positions
    out = [0] * len(a)
    for x in reversed(a):                 # reverse keeps equal keys in order
        count[x] -= 1; out[count[x]] = x
    return out

def radix_sort(a):                        # non-negative integers, base 10
    exp = 1
    while max(a) // exp > 0:
        buckets = [[] for _ in range(10)]
        for x in a: buckets[(x // exp) % 10].append(x)
        a = [x for b in buckets for x in b]
        exp *= 10
    return a

Bucket sort: spread values in [0, 1) into n buckets by int(x * n), sort each bucket (usually tiny) with insertion sort, and concatenate. O(n) on average for uniform data.

Shell sort

Insertion sort is slow because items move one step at a time. Shell sort first sorts items far apart (large gaps), so they make big jumps, then reduces the gap down to 1. Better gap sequences (Ciura: 1, 4, 10, 23, 57, 132, ...) give good practical performance.

What real libraries use (and recent advances)

Language / libraryAlgorithm
Python sorted, list.sortTimsort: finds already-sorted "runs" and merges them, with insertion sort for short runs. Since Python 3.11 it uses the Powersort merge policy (Munro and Wild), which chooses near-optimal merge orders. Stable.
JavaObjects: Timsort (stable). Primitives: dual-pivot quicksort (Yaroslavskiy), two pivots and three partitions.
C++ std::sortIntrosort: quicksort that switches to heap sort if recursion gets too deep, and to insertion sort for small ranges. std::stable_sort is a merge sort.
.NET Array.SortIntrosort (unstable); use LINQ OrderBy for a stable sort.
Go (since 1.19)pdqsort (pattern-defeating quicksort, Orson Peters 2016): detects patterns, adapts to sorted or few-unique input, guarantees O(n log n).
Rust (since 1.81)New implementations: driftsort for stable sort and ipnsort for unstable sort, both adaptive and faster than the previous ones.
GPUs, databasesRadix sort and bitonic / merge networks run thousands of threads in parallel; vectorised (SIMD) sorts such as Google's vqsort / Highway and Intel's x86-simd-sort speed up CPU sorting several times.
  • External sorting: when data exceeds memory, sort chunks that fit, write them as sorted "runs", then k-way merge the runs with a heap (see heaps). This is how databases sort huge tables.
  • Partial sorting: need only the top k? Use a heap (O(n log k)) or quickselect (O(n) average, std::nth_element, numpy.partition).
  • Sorting by key: sorted(people, key=lambda p: (p.dept, -p.salary)). Prefer key functions over comparison functions; they are computed once per item.

Real-world use cases

  • Databases: ORDER BY, sort-merge joins, building B-tree indexes in bulk, GROUP BY.
  • Search engines and feeds: ranking results by score (usually a partial sort / top-k).
  • Data analysis: medians, percentiles, removing duplicates, run-length encoding.
  • Computational geometry: sweep-line algorithms and convex hulls start by sorting points.
  • Compression: the Burrows-Wheeler transform (bzip2) is built on sorting rotations of the text.
  • Scheduling: greedy algorithms sort jobs by deadline, start or end time first.

Practice questions

Q1. Sort colours (0s, 1s and 2s) in one pass medium three-way partition

Dutch national flag partition with low / mid / high pointers (animated on the arrays page). O(n), O(1). Counting sort with two passes also works.

Q2. Merge two sorted arrays in place easy merge from the back

nums1 has room at the end for nums2.

def merge(a, m, b, n):
    i, j, k = m - 1, n - 1, m + n - 1
    while j >= 0:
        if i >= 0 and a[i] > b[j]: a[k] = a[i]; i -= 1
        else: a[k] = b[j]; j -= 1
        k -= 1

Filling from the back never overwrites unread data. O(m + n).

Q3. Sort a linked list medium merge sort

Split with fast/slow pointers, sort both halves recursively, merge (see linked lists). O(n log n) time, O(log n) stack. Merge sort is the natural choice for lists: no random access needed.

Q4. Largest number from a list medium custom comparator

Arrange numbers to form the largest number: [3, 30, 34, 5, 9] → "9534330".

from functools import cmp_to_key
def largest_number(nums):
    s = [str(x) for x in nums]
    s.sort(key=cmp_to_key(lambda a, b: (b + a > a + b) - (b + a < a + b)))
    return "0" if s[0] == "0" else "".join(s)

a goes before b if "a+b" is bigger than "b+a". This comparison is transitive, so sorting works.

Q5. Count inversions hard merge sort

How many pairs i < j have a[i] > a[j]? (A measure of how unsorted an array is.)

During the merge step, whenever an element from the right half is taken before remaining left-half elements, it forms an inversion with every one of them: add len(left) - i. O(n log n) instead of O(n²). A Fenwick tree also works.

Q6. H-index medium sorting / counting

The largest h such that h papers have at least h citations each.

Sort descending and find the last i with citations[i] ≥ i + 1: O(n log n). Or counting sort into buckets 0..n (anything above n goes into bucket n), then scan from the top: O(n).

Q7. Maximum gap between consecutive sorted elements in O(n) hard buckets / pigeonhole

With n numbers between min and max, the maximum gap is at least (max - min)/(n - 1). Use n - 1 buckets of that width; the answer is never inside a bucket, so track only each bucket's min and max, and compare each bucket's min with the previous non-empty bucket's max.

Q8. Sort characters by frequency medium count + bucket sort

"".join(c * f for c, f in Counter(s).most_common()): O(n log k), or bucket by frequency for O(n).

Q9. Minimum swaps to sort a permutation medium cycle decomposition

Map each value to its target index; the permutation splits into cycles. A cycle of length L needs L - 1 swaps, so the answer is n - (number of cycles). O(n log n) (for the sort that gives targets).

Q10. Wiggle sort (a[0] ≤ a[1] ≥ a[2] ≤ a[3] ...) medium greedy swaps

One pass: at even i, if a[i] > a[i+1] swap; at odd i, if a[i] < a[i+1] swap. Each swap fixes the current pair without breaking the previous one. O(n).

Q11. Is sorting stable? Why does it matter? easy concept

Sort orders by date, then stably by customer: each customer's orders stay in date order. With an unstable sort the second pass may scramble them. To sort by several keys in one go, use a tuple key: key=lambda o: (o.customer, o.date).

Q12. Sort an almost-sorted array (each element at most k from its place) medium heap of size k+1

Keep the next k+1 elements in a min-heap; the smallest of them must be the next output. O(n log k). Insertion sort is O(n·k), also fine for small k.
