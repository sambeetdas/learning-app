Caching

System design home

A cache keeps a copy of data in a faster place so repeated reads skip the slow path. Reading from Redis takes ~0.3 ms; the same data from a database query may take 5-50 ms; from another region, 100 ms or more. Because most workloads are skewed (a small share of items gets most of the reads), even a small cache absorbs a large share of the traffic. The hard parts are keeping it fresh, surviving its failures, and avoiding stampedes.

Caching strategies

How reads and writes interact with the cache

StrategyReadWriteTrade-off
Cache-aside (lazy loading)App checks cache; on miss reads DB and fills cacheApp writes DB, then deletes the cache keyThe default. Only caches what is used; first read is slow; brief staleness possible
Read-throughCache library loads from DB on missUsually paired with write-throughSimpler app code; cache must know the data source
Write-throughAlways warmWrite cache and DB synchronouslyFresh cache, slower writes, caches data nobody reads
Write-behind (write-back)Always warmWrite cache; flush to DB asynchronously in batchesVery fast writes; data loss if the cache dies before flushing
Refresh-aheadHot keys refreshed before they expire-No miss latency for hot keys; extra load for keys that go cold

Delete, don't update, the cached value after a write: two concurrent writers updating the cache can leave the older value in it. Even with deletes, a slow reader can write back a stale value, so keep TTLs as a safety net.

Eviction policies

When the cache is full, something must go. Simulate 20,000 requests over 1,000 items where popularity follows a Zipf (power-law) distribution, as real traffic does.

Hit rate by policy and cache size

  • LRU (least recently used): the common default; good for recency-driven workloads.
  • LFU (least frequently used): keeps long-term favourites; slow to adapt when popularity shifts. Modern caches (W-TinyLFU in Caffeine, Redis LFU mode) combine both.
  • TTL-based expiry bounds staleness regardless of policy; add random jitter so keys do not all expire at once.

Cache failure modes

Stampede and penetration

ProblemWhat happensFix
Stampede (thundering herd)A hot key expires; thousands of requests miss at once and hammer the databaseRequest coalescing (single-flight lock per key), refresh-ahead, serve stale while revalidating
AvalancheMany keys expire at the same moment, or the cache cluster restarts emptyJittered TTLs, warm-up, replicas, rate-limit DB fallbacks
PenetrationRequests for keys that do not exist always miss and hit the database (often an attack)Cache negative results briefly; a Bloom filter of valid keys
Hot keyOne key gets so much traffic that its cache shard saturatesReplicate hot keys, local in-process copies, key splitting
Stale dataThe cache serves values that changed in the databaseDelete on write, short TTLs, change-data-capture driven invalidation, versioned keys
Cache as a hidden dependencyThe database cannot handle the load if the cache disappearsCapacity-plan the fallback path or load-shed; treat the cache tier as critical infrastructure

Sizing a cache

  • Estimate the working set: the items read in a typical hour or day, times their size. The 80/20 rule is a starting guess; measure the real distribution.
  • Add overhead (keys, metadata, fragmentation: 20-50%) and replicas.
  • Target a hit rate from the database capacity: if the DB can serve 2,000 reads/s and you have 40,000 reads/s, you need a 95% hit rate.
  • Use the calculator to size memory.
