Architecture styles and API design

System design home

An architecture style is the overall shape of a system: how it is split into deployable parts and how those parts communicate. No style is best in general; each trades simplicity, team independence, scalability and operational cost differently. This page compares the main styles, shows key patterns in motion, and covers how to design the APIs between components.

Monolith vs microservices: one request

  • Find service boundaries with domain-driven design: bounded contexts (orders, payments, catalog) with their own language and data; avoid splitting by technical layer.
  • Database per service: services never read each other's tables; they use APIs or events. Shared databases create hidden coupling.
  • Do not start with microservices unless you already know the domain and have the platform (CI/CD, observability, service mesh) to support them.

Migrating: the strangler fig pattern

Replace a legacy system piece by piece: put a routing facade in front, move one capability at a time to new services, route its traffic there, and retire the old code when nothing uses it.

CQRS and event sourcing

CQRS (command query responsibility segregation) uses one model for writes (commands, validated against business rules) and separate, denormalised models for reads (queries), updated from events. Event sourcing stores the sequence of events as the source of truth; the current state is derived by replaying them. They are often used together, but each is useful alone.

Commands, events and read models

Benefits: read models optimised per screen, full audit history, time travel, easy new projections. Costs: eventual consistency between write and read sides, event versioning, snapshots for long streams, more moving parts. Use it for complex domains (finance, logistics, collaboration), not for simple CRUD.

Cells and deployment stamps

A cell (Azure calls it a deployment stamp) is a complete, independent copy of the application stack with its own data, serving a subset of tenants. A thin router sends each tenant to its cell. Failures and bad deployments are limited to one cell, and capacity grows by adding cells instead of making one giant deployment bigger.

Good API habits

  • Resources and nouns: POST /orders, GET /orders/{id}, GET /customers/{id}/orders; use HTTP status codes correctly (201, 400, 404, 409, 429, 503).
  • Pagination: prefer cursor-based (?after=opaque_cursor&limit=50) over offsets: stable under inserts and fast on large tables.
  • Idempotency: accept an Idempotency-Key header on POSTs that create things or move money; replay the stored response for duplicates.
  • Versioning: add fields freely, never change their meaning; use a version in the path or header for breaking changes and support the old one for a deprecation period.
  • Consistent errors: a machine-readable code, a human message, a correlation id (RFC 9457 "problem details").
  • Rate limits and quotas per client, with 429 and Retry-After.
  • Backends for frontends (BFF): a thin API per client type (web, mobile, partner) that aggregates back-end calls into exactly what that client needs.

More structural patterns

  • Hexagonal (ports and adapters) / clean architecture: business logic in the centre, independent of frameworks and databases; adapters at the edges. Makes testing and swapping infrastructure easy.
  • Sidecar and ambassador: run cross-cutting concerns (proxying, mTLS, logging) in a helper process next to each service (the basis of service meshes).
  • Anti-corruption layer: translate between a legacy or external model and yours so its concepts do not leak in.
  • Multi-tenancy: pooled (shared everything), siloed (dedicated per tenant) or hybrid; see the SaaS platform design.
