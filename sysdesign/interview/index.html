The system design interview playbook

System design home

A system design interview (or a real design review) is judged on how you think: clarifying the problem, making reasonable estimates, proposing a clean high-level design, going deep where it matters, and discussing trade-offs honestly. There is no single right answer. This page gives a repeatable structure, templates and the follow-up questions that come up again and again. Practise it with the case studies.

Step through the interview

The steps in detail

StepDoAvoid
1. Clarify requirementsWho are the users? Core features (pick 3-4)? Scale (DAU, data size)? Read/write ratio? Latency, availability and consistency needs? Mobile or web? Regions?Jumping into boxes before knowing what to build
2. EstimateQPS (average and peak), storage per year, bandwidth, cache size, servers. Round aggressively; state assumptionsSpending 10 minutes on arithmetic
3. API and data model3-6 key endpoints or events; main entities and their access patternsDesigning every field
4. High-level designClients, edge, gateway, services, data stores, caches, queues; walk through the main read and write pathsUnexplained boxes; a design that does not serve the requirements
5. Deep divesThe 1-3 hardest parts: hot keys, fan-out, consistency, ordering, matching, large files, ranking... Offer options and chooseGoing deep on trivial parts
6. Scale and reliabilityBottlenecks, sharding, replication, multi-region, failure modes, monitoring, security, costClaiming "it scales infinitely"
7. Wrap upSummarise, list trade-offs and what you would do next with more timeEnding mid-sentence

Clarifying questions checklist

Product

  • Who uses it and how? What are the top 3 use cases?
  • What is explicitly out of scope?
  • Any special features: search, notifications, analytics, offline?
  • Web, mobile, API, devices?

Scale and quality

  • Users (total, daily active), growth expectations
  • Requests per user per day, read/write ratio, peak factor
  • Data size per item, retention
  • Latency target, availability target, consistency needs
  • Global or single region? Compliance (GDPR, PCI, HIPAA)?

AI systems (extra)

  • What does "good" look like? How will we evaluate it?
  • Data sources, freshness, permissions
  • Latency (TTFT) and cost per request budgets
  • Hosted model API or self-hosted? Data residency?
  • Which actions can the AI take, and which need approval?

Classic trade-offs to name

Trade-offTypical framing
Consistency vs availability / latencyMoney and inventory: strong; feeds, likes, view counts: eventual
Push (fan-out on write) vs pull (fan-out on read)Push for normal users, pull for celebrities: the hybrid
SQL vs NoSQLRelationships and transactions vs known access patterns at huge scale
Synchronous vs asynchronousUsers wait only for what they must see; the rest goes through a queue
Precompute vs compute on demandStorage and staleness vs latency and CPU
Build vs buy (managed service)Control and cost at scale vs time to market and operations
Accuracy vs cost (AI)Bigger model or more retrieval vs latency and cost per request; route easy queries to small models

Common mistakes

  • Not asking about scale, then designing for either 100 users or a billion without saying why.
  • Single points of failure: one database, one region, one queue without replication.
  • Forgetting the read path is usually 10-100x busier than the write path.
  • Using a distributed transaction where an idempotent, eventually consistent flow would do.
  • Ignoring hot keys (celebrities, viral items, flash sales).
  • No mention of monitoring, security, data deletion (GDPR) or cost.
  • For AI designs: no evaluation plan, no guardrails, no cost or latency budget.
