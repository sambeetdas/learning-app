What a design has to satisfy

A design is only "good" relative to its requirements. Functional requirements say what the system does (users can post a photo, see a feed, search). Non-functional requirements (quality attributes) say how well: they drive almost every architectural decision, so pin them down with numbers first.

Latency numbers to know

Orders of magnitude matter more than exact values. Memory is ~1,000× faster than SSD, which is ~10× faster than a network round trip in the same data centre, which is ~100× faster than crossing an ocean.

How long things take (log scale)

  • Implication 1: keep hot data in memory (caches), and avoid chatty designs: 50 sequential database calls at 1 ms each already cost 50 ms.
  • Implication 2: the speed of light sets a floor: a round trip between Europe and the US west coast is ~150 ms. Serve users from nearby regions and edges.
  • Implication 3: disk seeks and cross-region calls do not belong in tight loops; batch and parallelise.

Throughput, latency and percentiles

Throughput is work per second; latency is time per request. Report latency as percentiles: p50 (median), p95, p99. Averages hide the slow tail that users actually notice. In systems that fan out (one page calls many services), the tail dominates: if each backend is slow 1% of the time, a request touching 100 backends is slow most of the time.

Tail latency amplification

Fixes: hedged requests (send a duplicate after the p95 time and use the first answer), timeouts, fewer and parallel calls, caching, and removing slow dependencies from the critical path.

Components in series multiply: a request that needs a load balancer (99.99%), a service (99.9%) and a database (99.95%) is available 99.99% × 99.9% × 99.95% ≈ 99.84%. Redundant components in parallel fail only if all fail: two independent 99.9% replicas give 1 - 0.001² = 99.9999%. Real failures are correlated (same zone, same bug), so redundancy must span failure domains.

Availability calculator

  • MTBF (mean time between failures) and MTTR (mean time to repair): availability = MTBF / (MTBF + MTTR). Cutting recovery time (automated failover, fast rollback) often buys more nines than making failures rarer.
  • SLA = a contractual promise; SLO = your internal target; SLI = the measurement (e.g. share of requests under 300 ms that succeed). See SRE practices.

CAP and PACELC

When a network partition (P) splits the nodes of a distributed database, it must choose between consistency (C), every read sees the latest write, and availability (A), every request gets a non-error answer. It cannot have both while the partition lasts. PACELC adds: else (no partition), you still trade latency (L) against consistency (C), because waiting for replicas to agree takes time.

Conflict resolution for multi-writer systems: last-writer-wins (simple, may lose updates), version vectors (detect conflicts, let the app merge), or CRDTs (data types that merge automatically, see collaborative editor).

Other fundamentals you will use everywhere

  • Idempotency: doing an operation twice has the same effect as once. Essential because networks retry. Use idempotency keys for writes (see payments).
  • Back-pressure: when a component is overloaded it must slow its producers down (queues with limits, 429 responses) instead of collapsing.
  • The fallacies of distributed computing: the network is not reliable, latency is not zero, bandwidth is not infinite, the network is not secure, topology changes, there is more than one administrator, transport has a cost, the network is not homogeneous.
  • Time: clocks on different machines drift; never rely on wall-clock order across machines for correctness. Use logical clocks, sequence numbers from a single writer, or bounded-uncertainty clocks.
