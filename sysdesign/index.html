System Design

← All topicsStart: Fundamentals →

System design is deciding how the pieces of a software system fit together so it meets its goals: the right features, fast enough, available enough, secure, affordable, and able to grow. It covers which components you need (load balancers, caches, databases, queues, models...), how data flows between them, where it is stored, and what happens when something fails.

This topic has two parts. Fundamentals pages teach the building blocks and the reasoning (estimation, databases, caching, messaging, reliability, security, AI systems). Case studies apply them end to end to real products, from a URL shortener to a payment system, a stock exchange, RAG assistants and multi-agent AI. Every design has animated request flows you can step through, capacity and compute estimates, the database choices and why, trade-offs, failure handling, and the matching Azure and AWS services and reference architectures.

How to approach any design

  1. Clarify requirements: functional (what it does) and non-functional (scale, latency, availability, consistency, cost, security). Agree what is out of scope.
  2. Estimate: users, QPS (average and peak), read/write ratio, storage, bandwidth, compute. This decides the architecture (see estimation).
  3. Define the API and data model: the main calls, the main entities, and where each lives (see choosing a database).
  4. Draw the high-level design: clients, edge, services, data stores, async paths. Walk through the key flows.
  5. Deep-dive the hardest parts: the hot path, the bottleneck, consistency, the tricky algorithm.
  6. Scale and harden: caching, partitioning, replication, queues, rate limits; what fails and how the system recovers.
  7. Discuss trade-offs and operations: monitoring, deployments, security, cost, and how it evolves.
