Estimating compute and choosing a database

System design home

Two decisions shape every design more than any other: how much capacity you need (servers, storage, bandwidth, GPUs) and where the data lives. Rough, order-of-magnitude estimates are enough: knowing whether you need 3 servers or 300, 50 GB or 50 PB, tells you which architecture is even possible. This page gives the method, rules of thumb, three calculators, and a decision tool for databases with the matching Azure and AWS services.

The estimation method

  1. Users: registered users → daily active users (DAU, often 10-50% of registered) → concurrent users (often 5-10% of DAU at peak).
  2. Traffic: actions per user per day × DAU / 86,400 = average requests per second (QPS). Multiply by a peak factor (2-10×) for the busiest minute.
  3. Split reads and writes: most products are read-heavy (10:1 to 100:1); this decides caching and replication.
  4. Storage: writes per day × size per item × retention × replication factor (+ indexes and overhead, often +30-50%).
  5. Bandwidth: QPS × response size (egress) and writes × payload size (ingress).
  6. Compute: peak QPS × CPU time per request / (cores per server × target utilisation) ⇒ servers; add spare capacity to survive losing a zone.
  7. Memory: cache the hot fraction of the data (often the 20% that receives 80% of reads) and count connections/sessions.
  8. Sanity check: compare with known systems and with the per-node limits below.

Little's law: how many requests are in flight?

Concurrency = throughput × latency. 3,000 requests/s that each take 200 ms means about 600 requests in progress at any moment. That number sizes thread pools, connection pools, WebSocket servers and GPU batch slots. Halving latency halves the concurrency you must hold.

Estimating GPUs and tokens for AI workloads

LLM serving is limited by two things: GPU memory (model weights plus the KV cache that grows with every token of every active request) and throughput (output tokens per second). Size for whichever runs out first. If you use a hosted model API instead, the same token numbers drive cost and quota (tokens per minute).

LLM serving calculator

  • Weights: parameters × bytes per parameter. A 70 B model is ~140 GB in FP16, ~70 GB in FP8, ~35 GB in INT4: it needs at least two 80 GB GPUs in FP16 before any KV cache.
  • KV cache per token ≈ 2 × layers × KV heads × head dimension × bytes. Models with grouped-query attention store far less (Llama-3-70B: about 0.3 MB per token in FP16). Long prompts (RAG, agents) multiply this.
  • Prefill vs decode: processing the prompt (prefill) is compute-bound and fast per token; generating (decode) is memory-bandwidth-bound and is usually the bottleneck. Time to first token grows with prompt length; inter-token latency grows with batch size.
  • Levers: quantisation, continuous batching, prefix (prompt) caching, smaller models for easy requests (routing), speculative decoding, shorter prompts, and capping output length. See AI foundations and the LLM serving design.

Choosing a database

Start from the access patterns (what you read and write, how often, how fast, with what guarantees), not from a favourite technology. Answer the questions and the tool ranks database families, with typical Azure and AWS services.

Questions to ask before choosing

  1. Data shape: rows with relationships, self-contained documents, key-value pairs, time-stamped measurements, a graph, text, vectors, files?
  2. Access patterns: lookups by key, range scans, ad-hoc queries and joins, full-text search, aggregations over months of data, similarity search?
  3. Consistency: do you need multi-row ACID transactions (money, inventory), or is per-item atomicity and eventual consistency enough (likes, views, feeds)?
  4. Scale: data size, read and write throughput, growth rate. Does it fit on one well-sized server (often yes, up to a few TB and thousands of writes per second)?
  5. Latency and geography: sub-millisecond? Users on several continents? Writes in several regions?
  6. Operations and cost: managed service availability, backups, team skills, licensing, cost per GB and per operation.

Polyglot persistence: most real systems use several stores

An online store typically uses a relational database for orders and payments, a document or key-value store for the product catalogue and carts, Redis for sessions and hot data, a search engine for product search, object storage for images, a stream for events, and a warehouse for analytics. Keep one source of truth per piece of data and feed the others from it (change data capture or events), rather than writing to several stores from the application.

Common mistakes

  • Choosing NoSQL "for scale" when the data fits comfortably in a managed relational database, then re-implementing joins and transactions in code.
  • Designing NoSQL tables like relational ones: in key-value and wide-column stores, design the keys from the queries (one table per access pattern is normal).
  • Hot partitions: a partition key with few values (country, today's date) concentrates load on one node.
  • Using the primary database for analytics; run reporting on replicas or a warehouse.
  • Storing large blobs in the database instead of object storage.
  • Ignoring how data will be deleted (retention, GDPR) and how it will be backed up and restored.
