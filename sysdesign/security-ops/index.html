Security, observability and cost

System design home

Three concerns cut across every design. Security: only the right people and services can do the right things, and data is protected wherever it is. Observability: you can tell what the system is doing and why, fast enough to fix problems before users suffer. Cost: the system stays affordable as it grows. Interviewers often reserve the last minutes for exactly these topics.

Authentication and authorisation

Authentication proves who you are; authorisation decides what you may do. Do not build your own identity system: use a standard protocol and a managed identity provider.

OAuth 2.0 + OpenID Connect: authorisation code flow with PKCE

Protecting data and the network

  • Encryption in transit (TLS 1.2+ everywhere, including internal traffic) and at rest (managed by the platform; customer-managed keys when compliance requires).
  • Envelope encryption: data is encrypted with a data key, which is itself encrypted by a master key in a key management service (Key Vault, KMS). Rotating the master key does not require re-encrypting all data.
  • Secrets live in a vault, never in code or config files; prefer identities that need no secret at all.
  • Network: private endpoints for databases and storage, no public IPs on back ends, WAF and DDoS protection at the edge, network segmentation.
  • Zero trust: never trust the network location; verify every request (identity, device, context), grant least privilege, assume breach and limit the blast radius.
  • Privacy: minimise collected data, classify PII, mask it in logs, honour deletion requests, keep data in the required region (data residency).
  • Application security: validate input, parameterise queries (SQL injection), encode output (XSS), check authorisation on every object (broken access control is the top web risk), rate-limit authentication endpoints, and keep dependencies patched.
  • Audit logs: record who did what, when, immutably; essential for incident response and compliance.

Observability: logs, metrics, traces

SignalWhat it isBest for
MetricsNumeric time series (request rate, error rate, latency percentiles, CPU, queue depth)Dashboards, alerting, capacity planning; cheap to store
LogsStructured events (JSON) with contextDebugging specific requests; expensive at volume, so sample and set retention
TracesThe path of one request across services as a tree of timed spansFinding which hop is slow or failing in a distributed system
ProfilesWhere CPU and memory go inside a processPerformance tuning

A distributed trace

  • Standardise on OpenTelemetry for instrumentation, and propagate a trace context (W3C traceparent) through HTTP calls and messages.
  • What to measure: the four golden signals (latency, traffic, errors, saturation); RED for services (rate, errors, duration); USE for resources (utilisation, saturation, errors).
  • Sampling: keep all errors and slow traces, sample the rest (tail-based sampling).
  • Cardinality: metrics labelled by user id or URL explode in cost; use bounded labels and put details in traces/logs.

SLIs, SLOs and error budgets

An SLI is a measurement of what users care about (share of checkout requests that succeed in under 500 ms). An SLO is the target (99.9% over 28 days). The error budget is what is left (0.1%): while budget remains, ship features; when it burns too fast, slow down and fix reliability. Alert on burn rate (how fast the budget is being consumed), not on every blip.

Incident practice: clear on-call ownership, runbooks, a severity scale, an incident commander for big events, status-page communication, and blameless post-incident reviews with tracked follow-up actions.

Cost driverLevers
ComputeRight-size instances, autoscale (and scale to zero), reserved instances / savings plans for steady load, spot/low-priority VMs for interruptible batch work, ARM-based instances
DatabasesChoose serverless or provisioned by load shape, cache reads, archive cold data, avoid over-provisioned throughput
StorageLifecycle rules to cool and archive tiers, compression, delete what you do not need, deduplicate
Network egressServe through a CDN, keep chatty services in the same zone/region, compress payloads
ObservabilitySample traces and logs, drop noisy debug logs, set retention per data type
AI / LLM tokensSmaller models for easy requests, prompt caching, shorter prompts and outputs, batch APIs for offline work, semantic caching (see AI cost)

Make cost visible per team, per feature and per tenant (tags, showback), and treat cost per request or per active user as a metric alongside latency and errors (FinOps).
