Reliability and resilience

System design home

At scale, something is always failing: a disk, a server, a zone, a dependency, a deployment, a certificate. Reliable systems assume failure and are designed so that a failure stays small (isolation), short (fast detection and recovery), and invisible to users where possible (redundancy and graceful degradation). This page covers the patterns that make that happen.

Core principles

  • Redundancy across failure domains: at least two of everything, spread over zones (and regions for the most critical systems).
  • Static stability: the system keeps working during a failure without needing to make changes (pre-provisioned capacity in surviving zones, no dependency on a control plane during recovery).
  • Fail fast and contain: timeouts, circuit breakers and bulkheads stop one slow component from consuming every thread in the fleet.
  • Degrade gracefully: serve stale data, drop optional features (recommendations, personalisation), and keep the core flow alive.
  • Make operations idempotent so retries are safe.
  • Detect fast: health checks, SLO-based alerts, synthetic tests (see observability).
  • Recover fast: automated failover, fast rollback, practised runbooks. Mean time to recovery often matters more than mean time between failures.

Timeouts, retries, backoff and jitter

Every remote call needs a timeout; without one, a hung dependency holds threads forever. Transient failures should be retried, but naive retries are dangerous: when a service recovers, every client retrying at the same moment creates a new spike that knocks it over again (a retry storm). Exponential backoff spaces retries out, and jitter (randomness) spreads them so clients do not synchronise.

Retry storm simulator: 1,000 clients after a 2-second outage

import random, time
def call_with_retries(fn, attempts=5, base=0.1, cap=5.0):
    for i in range(attempts):
        try:
            return fn(timeout=2.0)                      # always set a timeout
        except TransientError:
            if i == attempts - 1: raise
            sleep = random.uniform(0, min(cap, base * 2 ** i))   # "full jitter"
            time.sleep(sleep)
  • Retry only idempotent operations (or use idempotency keys); retry only transient errors (timeouts, 429, 503), never 400s.
  • Retry at one layer: retries at every layer multiply (3 attempts at each of 3 layers = 27 calls to the bottom service).
  • Use a retry budget (for example, retries may add at most 10% extra load).

Circuit breakers

When a dependency keeps failing, stop calling it for a while: fail fast (or serve a fallback) instead of waiting on timeouts. After a cool-down, let a few trial requests through; if they succeed, close the circuit.

Bulkheads, load shedding and rate limiting

Isolating failures

  • Bulkheads: separate thread pools, connection pools or even deployments per dependency or per customer tier, so one overwhelmed part cannot sink the ship.
  • Load shedding: when overloaded, reject excess work early (fast 503) rather than accepting everything and timing out on all of it. Prioritise: shed batch and background traffic before user-facing requests.
  • Rate limiting and quotas protect shared services from any single client (see the rate limiter design).
  • Shuffle sharding: assign each customer to a random small set of workers, so a "poison" customer can only affect the few other customers sharing exactly that set.
  • Cell-based architecture: run many independent copies (cells) of the whole stack, each serving a subset of customers; a bad deploy or failure affects one cell (see cells).

Disaster recovery: RPO and RTO

RPO (recovery point objective) is how much data you can afford to lose; RTO (recovery time objective) is how long you can be down. Both cost money: lower targets need more standby infrastructure.

Safe deployments

Most outages are caused by changes. Make every change gradual, observable and reversible.

Deployment strategies

  • Rolling: replace instances in batches; simple, no extra capacity; both versions run together briefly.
  • Blue/green: deploy the new version alongside, switch traffic at once, switch back to roll back.
  • Canary: send 1-5% of traffic to the new version, compare error rates and latency automatically, then expand in waves (zone by zone, region by region).
  • Feature flags separate deploying code from releasing features, and act as instant kill switches.
  • Backward-compatible changes (expand → migrate → contract) let old and new versions run side by side, which makes rollback safe.

Chaos engineering and testing

Inject failures deliberately in controlled experiments (kill instances, add latency, fail a zone, block a dependency) to verify the system degrades as designed. Start in test environments, then run small, well-monitored experiments in production. Load-test regularly at expected peak and beyond.
