Scaling, load balancing and the edge

System design home

Two ways to grow

Vertical scaling (scale up)

Use a bigger machine: more CPU, RAM, faster disks. No code changes and no distributed-systems problems. Limits: a hardware ceiling, cost that rises faster than capacity, and a single point of failure. The right first move for databases.

Horizontal scaling (scale out)

Add more machines behind a load balancer. Practically unlimited for stateless services and gives redundancy for free. Requires stateless design, load balancing, and for data: replication or partitioning.

Stateless is the key enabler: keep sessions in a shared store or signed tokens, files in object storage, and configuration in a config service, so any instance can serve any request and instances can be added, removed and replaced freely.

  • Health checks remove failed instances: shallow (process is up) vs deep (can reach its dependencies). Deep checks can cause fleet-wide flapping when a shared dependency is down, so many teams use shallow liveness plus careful readiness checks.
  • Connection draining lets in-flight requests finish before an instance is removed for a deployment.
  • Sticky sessions (affinity cookies) are a crutch for stateful servers; they unbalance load and lose sessions when a server dies.

Autoscaling

  • Reactive (target tracking): keep a metric near a target (CPU 60%, 100 requests per instance, queue length per worker). Add capacity fast, remove it slowly (cool-down) to avoid oscillation.
  • Scheduled: scale up before known peaks (9 am, Black Friday, a TV ad).
  • Predictive: forecast from history; useful when instances take minutes to start.
  • Scale on the right signal: CPU for compute-bound services, concurrency or latency for I/O-bound ones, backlog for workers, tokens or GPU utilisation for AI inference.
  • Mind the slow parts: instance start-up time, cache warm-up, database connection limits (use pooling), and downstream services that do not scale as fast as you do.
  • Scale to zero (serverless, Container Apps, Lambda) is cheapest for spiky or idle workloads, at the cost of cold starts.

The edge: CDN and global distribution

A CDN caches content in hundreds of locations near users, cutting latency and offloading origin servers; edge functions can run logic (redirects, auth checks, A/B splits) right there. Global load balancers use anycast (one IP announced from many places) or geo-DNS to route to the nearest healthy region. Full details are in the CDN topic and DNS topic.

When the data tier must scale too

Stateless tiers scale by adding instances; stateful tiers need replication for reads and partitioning (sharding) for writes and size. Caching (caching) and asynchronous processing (messaging) reduce how much they must scale.
