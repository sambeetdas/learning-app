Data: databases, replication and sharding

System design home

The data tier is where most designs succeed or fail: it holds state, so it cannot simply be cloned like a stateless service. This page covers the database families, how indexes and storage engines work, how data is copied (replication) for availability and read scale, how it is split (partitioning / sharding) for write scale and size, and how transactions work across all of that. To pick a database for a specific need, use the database chooser.

SQL vs NoSQL in one table

Relational (SQL)NoSQL (key-value, document, wide-column, graph)
SchemaDefined up front; migrations to changeFlexible per item (schema-on-read)
QueriesAny query, joins, aggregations (SQL)Designed around known access patterns (by key, by partition + sort key)
TransactionsMulti-row ACIDUsually per item or per partition; some offer limited multi-item transactions
ScalingVertical + read replicas; sharding is extra workHorizontal by design (automatic partitioning)
Best forBusiness data with relationships and integrity rulesHuge scale, simple access patterns, flexible or high-velocity data

Modern systems blur the line: PostgreSQL stores JSON and vectors; DynamoDB and Cosmos DB support transactions; distributed SQL (Spanner, CockroachDB, Aurora DSQL) scales SQL horizontally.

Indexes and storage engines

B-tree (most SQL databases)

A balanced tree of pages; reads are a few page lookups; updates modify pages in place. Great for reads and range queries; random writes cost random I/O. See B-trees.

LSM tree (Cassandra, RocksDB, many NoSQL)

Writes go to an in-memory table and are flushed as sorted immutable files, merged in the background (compaction). Excellent write throughput; reads may check several files (Bloom filters help). See LSM trees.

  • An index turns a full scan (O(n)) into a lookup (O(log n)), but every index slows writes and uses space. Index the columns you filter and sort by; use composite indexes in the order of your queries.
  • Covering indexes include all the columns a query needs, so the table is never touched.
  • Secondary indexes in NoSQL (global secondary indexes) are separate, eventually consistent copies of the data partitioned by another key.
  • Row vs column storage: row stores suit transactions (read a whole row); column stores (warehouses) suit analytics (read one column over billions of rows, compressed).

Replication

Keeping copies of the same data on several machines gives availability (survive a node or zone failure), read scale (serve reads from replicas), and lower latency (a copy near users). The hard part is keeping copies in agreement.

Leaderless (quorum)Write to W of N replicas, read from R; if W + R > N, reads overlap writesHighly available, no failover neededTunable consistency, read repair, more complexCassandra, Dynamo-style stores

Partitioning (sharding)

When one machine cannot hold the data or absorb the writes, split the data into partitions (shards), each owned by a different node. The partition key decides where each row lives, and it is one of the most important design decisions you will make.

Sharding strategies and resharding

StrategyProsCons
Range (A-F, G-M, dates)Efficient range scans; easy to understandHot spots (everyone writes "today"; popular letters); uneven sizes
Hash of keyEven spreadRange queries hit every shard; hash mod N moves almost all keys when N changes
Consistent hashingEven spread, adding a node moves only ~1/N of keysRange queries still scatter; needs virtual nodes for balance
Directory / lookup serviceFull control, move tenants individuallyAn extra lookup and a component to keep highly available
Geographic / tenantData residency, isolation, localityUneven tenant sizes; cross-tenant queries are hard
  • Hot partitions: a celebrity user or a viral item can overload one shard whatever the strategy. Mitigate with key salting (append a random suffix and merge on read), caching, splitting hot keys, or dedicated handling.
  • Cross-shard queries and transactions are expensive: design keys so that most operations touch one shard (e.g. partition orders by customer, not by order date).
  • Global secondary indexes answer queries by another key, at the cost of extra writes and eventual consistency.
  • Resharding online is hard: split ranges, copy data with dual writes, then cut over. Managed NoSQL stores do this automatically; plan headroom so you reshard rarely.

Transactions and isolation

Isolation levelPreventsStill allows
Read uncommitted-Dirty reads (seeing uncommitted data)
Read committed (common default)Dirty readsNon-repeatable reads, lost updates
Repeatable read / snapshotNon-repeatable readsWrite skew (two transactions each check a condition, both write)
SerializableAll anomalies: as if transactions ran one at a timeLower throughput, more aborts/retries
  • Optimistic concurrency: read a version number, write with WHERE version = v; retry on conflict. Ideal when conflicts are rare (ETags in APIs, Cosmos DB / DynamoDB conditional writes).
  • Pessimistic locking: SELECT ... FOR UPDATE; simple for hot rows such as seat inventory, but holds locks.
  • Across services or databases there is no shared transaction. Two-phase commit exists but blocks on coordinator failure; most systems use sagas with compensating actions and the transactional outbox (see messaging).

Storage types and data lifecycle

Tiering: keep hot data in the database or cache, warm data in cheaper storage, and archive cold data (object storage cool/archive tiers) with lifecycle rules. Backups: automated, tested restores, point-in-time recovery, and a copy in another region; define RPO and RTO (see disaster recovery).
