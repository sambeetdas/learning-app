What is a CDN and why use one?

A CDN is a network of servers spread around the world that sit between your users and your origin (the server that really owns the content). The first request for a file goes to the origin; the CDN keeps a copy, and later users nearby get that copy straight from a close-by edge server.

The three reasons to use one:

  • Speed: light in fibre takes roughly 1 ms per 100 km one way, so a round trip from India to a US origin costs well over 200 ms before any work is done. An edge in the same city cuts that to a few milliseconds, and also shortens TCP/TLS handshakes.
  • Offload: if 95% of requests are answered by the edge, the origin serves only 5% of the traffic, so it needs far less capacity and bandwidth.
  • Resilience and protection: traffic spikes and DDoS attacks are absorbed across hundreds of locations, and cached content can keep being served for a while even if the origin is down.

Pull vs push CDN

  • Pull (the normal one): the CDN fetches from your origin on demand and caches. Simple: just point it at your origin.
  • Push: you upload files to the CDN's own storage ahead of time. Used for large, rarely changing files (game patches, installers) where you control exactly what is where.

Request flow and the cache simulator

  1. The browser resolves the hostname (CNAME to the CDN) and connects to a nearby edge.
  2. The edge builds a cache key (usually host + path + selected query strings/headers) and looks it up.
  3. HIT: fresh copy found, served immediately.
  4. MISS: not cached or expired; the edge fetches from the origin (or shield), stores the response if the headers allow, and returns it.
  5. BYPASS / no-store: not cacheable (for example a personalised API), so every request goes to the origin; the CDN still adds TLS and network benefits.

    Caching rules and headers

    The origin tells the CDN (and browsers) how to cache with HTTP headers. Getting these right is 80% of CDN success.

    Header / directiveMeaning
    Cache-Control: max-age=NFresh for N seconds, in browsers and shared caches.
    s-maxage=NLike max-age, but only for shared caches (CDNs). Lets you cache longer at the edge than in browsers.
    public / privateprivate: only the user's browser may store it, not the CDN (per-user content).
    no-storeDo not store anywhere. Use for sensitive responses.
    no-cacheMay store, but must revalidate with the origin before every reuse (cheap with ETag).
    immutableThe file will never change at this URL; do not even revalidate. Pair with a long max-age and versioned file names.
    stale-while-revalidate=NServe a stale copy instantly while refreshing in the background for up to N seconds. Hides origin latency.
    stale-if-error=NIf the origin is failing, serve the stale copy for up to N seconds. Free resilience.
    ETag, Last-ModifiedValidators. The edge asks "has it changed?" (If-None-Match); the origin answers 304 Not Modified with no body.
    VaryLists request headers that change the response. Vary: Accept-Encoding is fine; Vary: Cookie or User-Agent shatters the cache into many copies.
    AgeResponse header: how many seconds the copy has been in a cache. Useful for debugging.

    The cache key

    Two requests share a cached copy only if their cache keys match. By default the key is the host and full URL. Decide deliberately what else belongs in it:

    • Query strings: ignore tracking parameters (utm_*, fbclid), include only the ones that change the content (?page=2). Otherwise every campaign link is a miss.
    • Headers: normalise Accept-Encoding (gzip/br) and, if needed, device class or language into a small set of values instead of passing the raw header.
    • Cookies: forwarding cookies to the origin usually makes the CDN treat each user as unique. Strip them for static content, whitelist only the ones that matter.

    Use cases

    Use caseHow a CDN helps
    Static websites and SPAsHTML, JS, CSS, fonts served from the edge. The origin can be plain object storage (S3, Azure Blob Storage).
    Images and mediaHuge bandwidth savings; many CDNs resize, crop and convert images to WebP/AVIF on the fly based on the requesting device.
    Video on demand and live streamingHLS/DASH split video into small segments (2-10 s) that cache well. Live manifests get a very short TTL, segments a longer one. Scales to millions of viewers without scaling the origin.
    Software and game downloadsLarge files, popular at release time. Range requests and segment caching let downloads resume and the edge cache big objects in chunks.
    Dynamic sites and APIsEven uncacheable responses go faster: the user does the TLS handshake with a nearby edge, which keeps warm, optimised connections to the origin. Cacheable API responses (catalogue, config, public data) can use short TTLs, such as 5-30 seconds.
    E-commerce and flash salesAbsorb the spike on product and category pages; keep cart and checkout dynamic.
    Global SaaSConsistent performance across regions; failover between origins in different regions.
    Security perimeterDDoS absorption, WAF, bot management, rate limiting, geo restrictions, TLS termination with managed certificates, all before traffic reaches the origin.
    Edge computeRun small functions at the edge: redirects, A/B tests, header rewriting, auth token checks, personalisation, image rules (Cloudflare Workers, CloudFront Functions / Lambda@Edge, Fastly Compute, Akamai EdgeWorkers).
    Protecting paid or private contentSigned URLs or signed cookies with an expiry, so only authorised users can fetch files through the CDN.

    Good

    • Lower latency and faster page loads worldwide.
    • Much lower load and egress cost on the origin.
    • Handles traffic spikes and attacks.
    • Built-in HTTP/2, HTTP/3, Brotli, TLS and image optimisation.

    Not so good

    • Stale content if caching is misconfigured; invalidation is not instant.
    • Another layer to configure, debug and pay for.
    • Personalised content needs care to avoid leaks.
    • Little benefit if all users and the origin are in one location, or for very low traffic.

    System design considerations

    Origin design

    • Lock down the origin: if users can bypass the CDN, they bypass its WAF and DDoS protection. Allow only the CDN: private storage with CloudFront Origin Access Control or Azure Front Door private link, CDN IP allow-lists, or a secret header the origin checks.
    • Origin failover: configure a secondary origin (another region or bucket) that the CDN switches to on errors or timeouts. Combine with stale-if-error.
    • Use an origin shield: raises the hit ratio and reduces origin load, at the cost of slightly higher latency on a full miss and a small extra fee.
    • Request collapsing: when 1,000 users ask for the same missing file at once, the edge should send one origin request and make the rest wait. Check that this is enabled, especially for large files and live video.
    • Cache negative responses carefully: briefly cache 404s to protect the origin; do not cache 5xx errors for long.

    Delivery and deployment

    • Separate static and dynamic: e.g. /static/* and /assets/* with a long TTL, /api/* with no caching, using path-based behaviours/rules on one domain.
    • Deploy safely with a SPA: upload new fingerprinted assets first, then update index.html. Keep old assets for a while so users with a cached HTML still find their JS.
    • Compression: serve Brotli or gzip for text; never double-compress images.
    • Protocols: enable HTTP/2 and HTTP/3 (QUIC) at the edge; the CDN can talk HTTP/1.1 to a simple origin.
    • TLS: use CDN-managed certificates on your custom domain; keep the CDN-to-origin hop on HTTPS as well.
    • CORS: if responses vary by Origin, add it to the cache key or Vary, or a response cached for one site may be served to another and fail.
    • Multi-CDN: large players use two or more CDNs behind DNS-based steering for resilience and price leverage. Costs: duplicate configuration and uneven features.

    Security

    • DDoS and WAF: attacks hit the huge edge network instead of your origin; WAF rules block injection, bots and abusive IPs at the edge.
    • Cache poisoning: an attacker sends a request with an unexpected header (for example X-Forwarded-Host) that the origin reflects into the response, and the CDN caches the poisoned response for everyone. Keep headers that influence the response either in the cache key or ignored by the origin.
    • Web cache deception: a user-specific page that is wrongly cached because of its URL (like /account/profile.css) can be fetched by someone else. Base caching on explicit headers, not only file extensions, and send private, no-store for personal pages.
    • Never cache responses with Set-Cookie or authenticated data unless the cache key includes the identity on purpose.
    • Signed URLs / cookies, token authentication, hotlink protection, geo-blocking control who may fetch content.
    • Subdomain takeover: a DNS CNAME left pointing at a deleted CDN endpoint can be claimed by someone else. Clean up DNS when you remove an endpoint (see DNS security).

    Metrics and cost

    MetricWhy it matters
    Cache hit ratio (requests and bytes)The headline number. Static sites should be above 90%. A low ratio usually points to cache-key problems (cookies, query strings, Vary) or too-short TTLs.
    Origin offload / origin requests per secondWhat your servers actually see; size the origin for the miss rate, not the user rate.
    Time to first byte (p50/p95/p99) by regionShows whether users get the speed benefit, and where.
    4xx / 5xx rate, origin errors, timeoutsCatches broken deploys and origin outages early.
    Bandwidth and request countsMain cost drivers: data transfer out, HTTP requests, invalidations, and extras such as edge compute, WAF rules and log delivery. Edge egress is usually cheaper than origin egress.

    Common pitfalls

    • Everything is a miss: cookies forwarded to origin, Vary: Cookie, unique query strings, or Cache-Control: no-cache/private set by the framework by default.
    • Caching the wrong thing: personal data, error pages, redirects to login. Verify with real requests before going live.
    • Users see an old version: long TTL on a non-versioned file. Fingerprint file names or shorten the TTL; remember browsers cache too.
    • Origin falls over after a purge: purging everything sends all traffic to the origin at once. Purge narrowly, use soft purge, or enable a shield and request collapsing.
    • Uncached big files: some CDNs only cache objects up to a size limit unless range caching is enabled.
    • Forgetting the browser cache: a CDN purge does not clear what is already in users' browsers.
    • Debugging blind: not knowing which edge answered; use the debug headers below.

    Quick reference

    • Static files: fingerprint the names, max-age=31536000, immutable.
    • HTML: short s-maxage with stale-while-revalidate and stale-if-error.
    • Personalised / sensitive: private, no-store, and keep it out of the CDN cache.
    • Big audience or video: enable shield and request collapsing; test at expected peak.
    • Always: lock down the origin, monitor hit ratio, and plan how you will invalidate before you need to.
